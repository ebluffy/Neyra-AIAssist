## 1. Краткое резюме проделанной работы

В рамках четвёртого этапа («Прогон интерфейса на баги + «Провайдеры» как в OpenBot») веб-клиент `web/` монорепозитория Neyra доведён до уровня надёжного, строгого и честного продукта:

1. **Исправлены все подтверждённые дефекты B-1..B-10** на всех контрольных разрешениях (десктоп 1440px, планшет 1024px, 768px, мобильные 390px, 360px и при масштабировании браузера Zoom 200%).
2. **Внедрена архитектура провайдеров OpenBot**:
   - Адаптивная сетка карточек API-провайдеров (1 колонка на 390px, 2 на 768px, 3 на 1440px+).
   - In-place машина состояний ввода и проверки ключа прямо на карточке:  
     `empty` → `typing` → `verifying` → `verified` / `failed` → `saving` → `saved` (скрыт).
   - BFF-эндпоинт проверки шлюза `POST /api/admin/providers/[name]/verify` с тайм-аутом 8 секунд, защитой от зависаний, замером сетевой задержки (latency ms) и нормализацией списка моделей.
   - Выделенный полнофункциональный экран провайдера внутри модального окна админки с хлебными крошками, базовыми параметрами, списком полученных от API моделей, системными лейнами (talk, brain, coding, vision) и подтверждением удаления через ввод имени слага с проверкой блокировок.
   - Двухшаговое модальное окно добавления провайдера: Шаг 1 — каталог готовых пресетов (OpenAI, Anthropic, OpenRouter, Groq, DeepSeek, Ollama, vLLM, Custom), Шаг 2 — форма параметров и предварительная проверка связи.
   - Блок интеграции с локальным CLI-мостом OpenCode (`opencode auth login`) с копированием команды и разъяснением статуса.
3. **Очищен раздел «Интеграции»**:
   - Удалены дублирующие карточки LLM-провайдеров и дублирующие списки моделей.

4. **Унифицирован экран настроек (`SettingsDialog`)**:

   - Полностью искоренены выдуманные данные: статус Discord проверяется по реальному пользователю сессии (никаких захардкоженных `alexey#0001` или фиктивных person_id).

## 3. Архитектура провайдеров OpenBot

Внедрён единый центр управления LLM-провайдерами по стандартам OpenBot:

### 3.1. Карточки провайдеров и машина состояний ключа (In-Place Key Lifecycle)
Каждая карточка отображает:
- Иконку провайдера с фирменным стилем и бейджем (`Встроенный` / `Свой` / `Локальный`).
- Статус подключения (зелёный индикатор при наличии ключа или для локальных инстансов, нейтральный — если ключ не задан).
- Количество доступных моделей и список используемых системных лейнов.
- In-place поле ввода ключа:
  - Если ключ сохранён: отображается кнопка «Сменить ключ» или «Удалить ключ». Сам ключ **никогда не отображается в DOM и не попадает в логи**.
  - При вводе: кнопка «Проверить» активирует BFF `/verify`.
  - При успешной проверке: выводится зелёная плашка с замером latency (например, `42 мс, 18 моделей доступно`).
  - При ошибке: выводится понятное сообщение об ошибке (например, `401 Неверный API-ключ` или `Тайм-аут соединения (8с)`).
  - При сохранении: ключ передаётся на сервер и очищается из клиентского стейта (`setKeyInput('')`).

### 3.2. BFF-эндпоинт верификации (`POST /api/admin/providers/[name]/verify`)
- Реализован в `web/src/app/api/admin/providers/[name]/verify/route.ts`.
- Устанавливает жёсткий `AbortController` с тайм-аутом **8000 мс**.
- Проверяет доступность эндпоинта моделей (`${base_url}/models` или кастомный путь).
- Предупреждает о небезопасном протоколе HTTP для внешних хостов (для `localhost`/`127.0.0.1` разрешён).
- Возвращает стандартизированный плоский JSON-ответ:
  ```json
  {
    "ok": true,
    "models_count": 18,
    "latency_ms": 42,
    "models": ["gpt-4o", "gpt-4o-mini", "o1"]
  }
  ```
- Покрыт 6 интеграционными юнит-тестами (`web/src/app/api/admin/providers/[name]/verify/route.test.ts`).

### 3.3. Выделенный экран провайдера (Provider Screen)
При нажатии на карточку провайдера внутри модалки открывается детальный экран с навигацией «Назад к списку»:
1. **Шапка**: иконка, имя, статус, проверка связи.
2. **Параметры подключения**: базовый URL, тип провайдера, валидация.
3. **Ротация API-ключа**: безопасное обновление секрета с подтверждением.
4. **Список моделей**: модели, обнаруженные при живом зондировании эндпоинта.
5. **Системные лейны**: привязка провайдера к системным ролям (`talk`, `brain`, `coding`, `vision`).
6. **Опасная зона**: удаление провайдера с модальным окном подтверждения (требуется ввод точного имени слага провайдера) и запретом удаления, если провайдер назначен в активный системный лейн.

### 3.4. Двухшаговое добавление провайдера
- **Шаг 1**: Каталог пресетов (OpenAI, Anthropic, OpenRouter, Groq, DeepSeek, Ollama, vLLM, Кастомный OpenAI-совместимый).
- **Шаг 2**: Форма параметров с автозаполнением базового URL, подсказками формата ключа, инлайн-проверкой и кнопкой сохранения.

### 3.5. Блок OpenCode CLI
- Интеграция с локальным терминальным шлюзом OpenCode.
- Модальное окно «Авторизация в OpenCode CLI» с копируемой командой `opencode auth login`.
- Модальное окно «Установка OpenCode CLI» с командой `curl -fsSL https://opencode.ai/install.sh | bash`.
- Честное описание: «После выполнения команды локальный демон OpenCode сохранит сессионный токен. Веб-интерфейс автоматически обнаружит авторизацию при перезапуске ядра».

1. **Сервер ядра (`server/`) и Tauri-клиент (`client/`)**: не модифицировались.
2. **Публичный стенд `https://neyra.owyx.site` и системные сервисы `/opt/neyra/**`**: не деплоились, не перезапускались, конфиги и базы стенда не затрагивались.

4. **Секреты и ключи**: ключи API провайдеров не сохраняются в открытом виде в DOM или localStorage, поля ввода имеют тип `password`, атрибуты `autocomplete="new-password" spellcheck="false"`, состояние очищается сразу после подтверждения сохранения.
