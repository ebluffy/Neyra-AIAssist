## Реализованная основа и постоянные правила

Этапы 1a–1d и 2 завершены: аудит, перенос server/client/devtools, слои конфигурации, роли LLM-провайдеров и единый Control API. Их подробные чеклисты и старые прогоны удалены из рабочего плана; история остаётся в Git и [VERSION.md](VERSION.md).

- `server/core/` — ядро, API, память и общие сервисы; `server/modules/` — интеграции; `server/dashboard/` — серверная ops-панель.
- `client/` — самостоятельное приложение Windows/Linux (Tauri 2 + React + TypeScript, ТЗ — §3b): первая поставка шагов 1–3 — оболочка, чат, PTT-голос, host bridge; шаги 4+ — план. Исходники dashboard в него не копируются. Клиент не оркестрирует агента и не хранит серверную память.
- `devtools/mcp_server/` — только разработка, не runtime-поставка.
- Бизнес-логика, память, LLM/STT/TTS, оркестрация инструментов и Event Bus остаются на сервере. Локальные OS-операции на ПК пользователя исполняет опциональный `host bridge` клиента (§3b), под локальной политикой разрешений. Изменение `core/` должно быть обосновано задачей, которую нельзя закрыть модулем или существующим API.
- Конфигурация: `server/config.yaml` + тематические `server/config/*.yaml` и конфиги модулей; источники типов/defaults — tracked examples и schema. Роли моделей задаются через `llm.*_model` и `llm.providers.*`, без привязки к одной постоянной модели.
- Секреты — `server/.env`; память — `server/data/` либо настроенный `paths.data_dir` / `NEYRA_DATA_DIR`. Конфиги, persona, память, модели и логи не включаются в коммит и не затираются при обновлении.
- Control API — `server/core/api/`, не отдельный модуль. Loopback по умолчанию; внешний доступ требует auth/ролей. Модули взаимодействуют через API и Event Bus.
- Общие инструкции: `docs/en/` и `docs/ru/`. Рабочие задачи — здесь, история поставок — в VERSION.

## 3. Веб + ядро, затем клиент Windows/Linux

Этап 3 делится на две части: сначала допиливаем **веб-панель и поведение Нейры**, потом отдельным подэтапом — полноценный клиент Windows/Linux.

### 3a. Веб-панель и ядро Нейры (сейчас)

Серверная реализация, dashboard и исправления pipeline установлены на MiniPC. Остаются live-приёмка моделей и интеграций, проверки багов ниже и отдельный будущий клиент. Исторические отчёты AR и промежуточные прогоны здесь больше не дублируются.

`server/dashboard/` — ops/admin control plane (статус, модули, память, система, вебхуки, настройки, docs), пока нет десктоп-клиента. `client/` остаётся самостоятельным приложением со своим UI; исходники dashboard туда не копируются. Возможный общий пакет API-контрактов требует отдельного решения. UI сейчас на русском; полная ru/en-локализация открыта в §14.

**Люди (память):** account-first карточки, accounts/aliases и свободные `person_facts`; анкетных полей нет (§7). CRUD в дашборде; агент обновляет через tools.

Модули в вебе: действия по `lifecycle` (resident → PATCH enabled **с авто soft-restart ядра**; on_demand → invoke; общий enable/config). В дашборде модуля: вкладки «Управление / Конфиги / Логи», загрузка `.zip` (`POST /v1/plugins/upload`), удаление (`discord` защищён), правка конфиг-файлов (`/v1/plugins/{id}/files`), хвост логов (`/v1/logs`). #### BUG-07/08: локальное расследование GIF → музыка

Проверено 2026-10-19 на синтетических строках и заглушках, без Discord/LLM/voice-вызовов. На скриншоте нет исходного URL/metadata, поэтому конкретный обход в сообщении друга пока не установлен.

- **Любой HTTP(S) URL становится play-кандидатом:** `music_intent.py:candidate_music_intent` не требует музыкального намерения или поддерживаемого хоста; `plan_music_route` сразу выбирает `PLAY_MUSIC`, без классификатора. Воспроизведено для Tenor без отдельного `gif` в пути, Giphy `/gifs/`, Discord CDN `.mp4` и обычной ссылки на статью.
- **GIF-фильтр неполный:** `plan_music_route` проверяет только отдельные слова `gif|гифк|мем`, без metadata/домена. «Гифка/гифку» не совпадают с `гифк`; наличие `gif` в URL защищает лишь часть ссылок. Контрольный Tenor `…-gif-123` без других сигналов остаётся `CHAT`.
- **Слова внутри URL считаются командами:** `play` в slug включает play-verb и обходит GIF-защиту; `stop` в URL без GIF-маркера выбирает `music.stop`. Команды проверяются по всему тексту до отделения URL. Отдельно воспроизведены ложные play-намерения «не включай …» и «поставь реакцию на гифку».
- **Классификатор может обойти фильтр:** после подавления hard candidate остаются soft hints. При подставленном `PLAY_MUSIC` строки «мем про музыку» и Tenor `…spotify-gif-123` проходят `soft_play_allowed` и запускают музыку. Это подтверждённый условный путь, не доказательство ответа настоящего классификатора в эпизоде друга.
- **Медиа не участвуют в решении:** `bot.py:on_message` передаёт маршрутизатору только текст. `_collect_image_attachments` читает attachments, но не embed-медиа Tenor/Giphy; результат vision не блокирует ложное play-намерение. По коду чистый image/GIF attachment без ссылки идёт отдельным путём vision с первым кадром; сам по себе он не объясняет срабатывание URL-ветки.
- **Проверка ссылки слишком поздняя:** `music.py:_handle_action_async` проверяет Lavalink/войс и может подключить player до `_normalize_play_query`. На заглушках для Giphy без войса получено точное `join a voice channel first`, нормализация ещё не вызывалась. Для пользователя в войсе код подключения также расположен раньше отказа «только YouTube».
- **Пробел регрессий:** существующий GIF-тест проверяет лишь «покажи смешной gif» и «play gif song»; он и offline music-script проходят при воспроизводимых ошибках выше. Нужны случаи реальных форм URL, embed/attachment, русских словоформ, команд в slug, отрицаний и classifier soft-path; неподдерживаемое медиа не должно подключать voice или публиковать `MUSIC_*`. Сохранить положительные сценарии явных музыкальных команд и поддерживаемых YouTube-ссылок. Локальное исправление и расширенные регрессии реализованы; live-регрессию выполняет пользователь после обновления стенда.

- [x] Для BUG-07/08 проверять URL до подключения войса: автоматический play допускает только поддерживаемые музыкальные ссылки, сейчас YouTube. Tenor/Giphy/Imgur и Discord CDN не считать музыкой. Команды распознавать вне URL; classifier не должен обходить media guard. Проверить ссылки, вложения, отрицания и отсутствие voice/Lavalink-вызовов для неподдерживаемых медиа.

### 3b. Клиент для Windows и Linux — после серверной части

Клиент — **Tauri 2 + React + TypeScript (Rust backend + WebView UI)** для Windows и Linux. Это самостоятельный UI в `client/`, исходники `server/dashboard/` в него не переносятся. Реализация начинается после серверных блокеров (§15); на 2026-10-31 в текущей ветке реализуется первая поставка шагов 1–3 (§3b.11), на основе серверных исправлений PR #34, смёрженного в main 2026-10-31. Windows остаётся минимумом защиты из §0. Linux (CachyOS KDE Wayland + NVIDIA у владельца) и Windows по решению владельца 2026-10-31 поддерживаются **на равных**. Ниже описана целевая функциональность (ТЗ), а не уже доступные возможности.

#### 3b.1. Продуктовое видение

Нейра на ПК — **глобальный ИИ-ассистент на компьютере пользователя**. Он собран из четырёх идей, но реализован по-своему:

| Источник идеи | Что берём |
| --- | --- |
| **Grok Bot** | Умный агент с опциональным управлением ПК: CLI/FS, браузер, GUI, многошаговые задачи с проверкой результата. |
| **ChatGPT live voice** | Голосовой режим «просто разговариваем»: непрерывный диалог, перебивание (barge-in), естественные паузы, без кнопок на каждую реплику. |
| **JARVIS** | Быстрые команды: короткая фраза или хоткей сразу запускают заранее описанное действие без долгих рассуждений LLM. |
| **Desktop Mate** | Опциональный 3D-персонаж поверх рабочего стола («свой VTuber на компьютере»). |

«Мозг» (LLM, память, рассуждения, выбор шагов), **STT и TTS** живут на сервере (`server/core/`, MiniPC). `client/` — «лицо», уши/рот (захват микрофона, проигрывание звука) и опциональные «руки» Нейры на машине пользователя. Это отдельная поверхность исполнения, **не §9**: §9 — изолированный стол самой Нейры на её сервере/MiniPC.

С Нейрой одинаково удобно общаться **голосом и текстом**; текстовый и голосовой ход проходят один и тот же серверный pipeline и общую историю private-сессии.

#### 3b.2. Решения владельца (2026-10-31)

- 3D-персонаж есть, но **выключен по умолчанию**; включается в настройках.
- Голос и текст — равноправные способы общения.
- Активация голосом — несколько режимов на выбор: по умолчанию wake word **«Нейра»** + команда; режим «слушать всегда»; push-to-talk (хоткей/кнопка).
- STT и TTS выполняются **на сервере**; клиент только захватывает/стримит микрофон и проигрывает аудио.
- Полная реализация TTS+STT (голосовой модуль) идёт **вместе с десктоп-приложением**, а не после ВКР.
- Права на ПК по умолчанию: **безопасное делает сама, перед опасным спрашивает** (карточка `Разрешить / Отклонить`).
- Быстрые команды создаются тремя способами: интерфейс, голос («запомни команду…»), конфиг.
- К защите ВКР владелец хочет **всё**, включая персонажа (§0 при этом не меняется; см. 3b.11).

#### 3b.3. Экраны и окна клиента

1. **Подключение:** адрес сервера и токен; хранение в Windows Credential Manager и системном хранилище Linux (Secret Service / KWallet; адаптер выбрать при реализации), не открытым текстом. Проверка совместимости версии API.
2. **Чат:** server-side history, streaming, вложения, озвучка ответа (кнопка/авто), индикатор моделей хода (как отчёт #27).
3. **Голос (live-режим):** полноэкранный/компактный режим разговора без текста — визуализация уровня микрофона и речи Нейры, статус `слушаю / думаю / говорю`, кнопки «пауза микрофона» и «завершить разговор».
4. **Статус:** health, modules, models, API version (экран «Статус», не «Дашборд»).
5. **Модули:** список, состояние, enable/disable, start/stop, мягкий рестарт по существующим API/ролям.
6. **Быстрые команды:** список, создание/редактирование, тест-запуск, импорт/экспорт (3b.5, хранение — 3b.10).
7. **Доступ к ПК:** мастер-тумблер, контуры, режимы, allowlist/deny-list, журнал действий (3b.8–3b.9).
8. **Персонаж:** вкл/выкл, выбор `.vrm`, размер/позиция/монитор, набор анимаций, реакции, производительность (3b.6).
9. **Настройки:** голос (режим активации, wake word, устройство микрофона/вывода, громкость, VAD-чувствительность), хоткеи, тема, автозапуск, обновления, графический режим Linux (блок Owyx ниже).
   - **Сервер (бэкенд):** URL сервера, кнопка «Проверить подключение» (health + версия API), токен/сопряжение устройства, имя этого ПК; несколько **профилей серверов** с добавлением и переключением (токен каждого — в системном хранилище секретов).
10. **Трей и оверлей:** иконка в трее с быстрыми действиями; компактный плавающий command bar / HUD по глобальному хоткею поверх окон.
11. **Вторая волна UI:** Monaco для промптов/конфигов/модулей, просмотр серверных логов, import/export модулей.

Клиент открывается без сервера и показывает состояние «сервер недоступен»; удалённые действия, голос и управление ПК в этом состоянии недоступны.

#### 3b.4. Голосовой модуль: STT, TTS и live voice

Серверная основа уже есть и переиспользуется: `server/core/voice/` (`stt.py`, `tts.py`, `yandex_tts.py`, `config.py`), конфиг `server/config/voice.yaml` (пример `voice.example.yaml`: STT lanes `local` faster-whisper / `cloud` deepgram/openrouter/groq, TTS lanes), `server/scripts/voice_preflight.py`. Модуль `server/modules/local_voice/` пока заглушка (`enabled: false`) — его роль пересмотреть: голосовой цикл ПК-клиента живёт на сервере как сервис ядра/API, а не как локальный микрофон MiniPC. Discord-голос (§11) — отдельный контур, не блокирует и не блокируется.

- **Транспорт:** отдельный WSS-канал голосовой сессии (новый контракт, не расширение проверенного chat streaming): клиент стримит PCM/Opus-фреймы микрофона, сервер возвращает частичные/финальные транскрипты, события хода и аудиочанки TTS. Версия схемы, `session_id`, отмена, лимиты размера и длительности.
- **STT на сервере:** потоковое распознавание (streaming, где провайдер умеет; иначе сегменты по VAD), частичные гипотезы для UI, язык из `voice.language`. Провайдеры и fallback — через существующие lanes `voice.stt`.
- **TTS на сервере:** потоковая озвучка по предложениям, чтобы первая фраза звучала до конца генерации ответа; формат и частота согласуются в handshake; клиент буферизует и проигрывает. Ответ для голоса — простой текст без Markdown (правило формата вывода по потребителю).
- **Режимы активации** (выбор в настройках, по умолчанию wake word):
  1. **Wake word «Нейра» + команда.** Детектор ключевого слова работает **локально на ПК пользователя**: звук не уходит на сервер, пока слово не распознано; после срабатывания фраза-команда стримится в серверный STT. Детектор должен быть **лёгким**: **openWakeWord** (Apache-2.0) с собственной моделью «Нейра», обученной на синтетических данных (TTS-сгенерированные произношения + шум/негативы), без записи голоса владельца. Porcupine рассмотрен и отклонён: коммерческая лицензия и ключ доступа. Бюджет: ≤ ~2–3% одного ядра CPU и ≤ ~50–100 МБ RAM в режиме ожидания на среднем ноутбуке, без GPU; задержка срабатывания ≤ ~0,5 с. Детектор в отдельном потоке Rust (или sidecar), выключается вместе с микрофоном; ложные срабатывания на похожие слова и порог чувствительности настраиваются. Бюджет проверяется замером на обеих ОС (блок Owyx «Производительность»).
  2. **Слушать всегда:** клиентский VAD режет речь на фразы и отправляет только их; явный индикатор «микрофон активен» всё время.
  3. **Push-to-talk:** глобальный хоткей или кнопка в оверлее/трее; на Wayland — через GlobalShortcuts portal, при недоступности — видимая кнопка.
- **Live voice (идея ChatGPT voice mode):** непрерывный дуплексный диалог: VAD определяет конец реплики, Нейра отвечает голосом, пользователь может **перебить** (barge-in) — клиент гасит воспроизведение, сервер отменяет текущую генерацию/TTS и принимает новую реплику. Эхоподавление (AEC) обязательно, иначе Нейра слышит сама себя. Короткие подтверждения («угу», «секунду») и честный статус при задержке провайдера (BUG-04).
- **Приватность:** микрофон включается только с явного разрешения; индикатор записи; аудио по умолчанию не сохраняется, в истории остаётся транскрипт. Голосовой ход не даёт больше прав, чем текстовый; опасные действия по-прежнему требуют карточки (или явного голосового подтверждения, если владелец включит этот режим — отдельно от wake word).

#### 3b.5. Быстрые команды (JARVIS-контур)

Серверный `agent.fast_path` в `server/config/agent.yaml` (пример `server/config/agent.example.yaml`: regex-allowlist однозначных команд до brain, `enabled: false`, `intents[]` с `name`, `patterns`, `event_type`, `target`; пример `light_off` → `home.light.turn_off`) **остаётся серверным** механизмом для серверных событий (умный дом и т.п.). **Пользовательские быстрые команды ПК в него не пишутся** и хранятся только локально у клиента (3b.10); схему триггеров можно взять по образцу `fast_path`.

- **Модель команды:** `name`, триггеры (фразы/regex, хоткей), действие (`event_type` на сервере **или** `client_tool` с фиксированными параметрами, например «открой Steam», «режим работы» = набор приложений/окон/громкость), требуемый контур/уровень риска, нужно ли подтверждение, ответ голосом.
- **Исполнение:** совпадение триггера → действие без полного хода brain; неоднозначность → обычный ход LLM. Быстрая команда не может обойти локальную политику ПК: опасное действие внутри неё всё равно требует карточки.
- **Три способа создания** (одна схема, одно локальное хранилище `Neyra/commands/` у клиента):
  1. **UI** — экран «Быстрые команды» (форма + тест-запуск).
  2. **Голос/чат** — «Нейра, запомни команду: когда я говорю „режим игры“, открой Steam и Discord». Сервер разбирает фразу и возвращает черновик команды; клиент показывает карточку и сохраняет её **локально** только после подтверждения.
  3. **Файл** — `Documents/Neyra/commands/*.yaml` правится и вручную, и в приложении: hot-reload по изменению файла, валидация схемы, ошибки (файл, строка, причина) показываются в UI/уведомлении; битый файл не ломает остальные команды, последняя валидная версия остаётся активной.
- **Синхронизация с сервером только в рантайме:** активные команды (имена, триггеры, тип действия, без секретов) клиент объявляет в capabilities handshake и обновляет при изменении; сервер держит их в памяти **сессии этого клиента** только для распознавания голосом/текстом из приложения и **не сохраняет** на диск или в память Нейры. Совпадение триггера на клиенте (хоткей/текст) исполняется локально без сервера, если не нужен ответ LLM.
- **Только из приложения:** пользовательские быстрые команды работают **только из десктоп-приложения пользователя** (голос/текст в клиенте). Из Discord, Telegram, dashboard и любых других каналов они недоступны вообще — независимо от того, включён ли ПК. Серверный `agent.fast_path` — отдельный механизм, это правило его не касается.
- **Экспорт/импорт и обмен:** команды и настройки свои на каждом ПК. «Экспорт» открывает нативный диалог «Сохранить как» (Tauri `@tauri-apps/plugin-dialog`) и сохраняет файл конфига (`settings/`, `commands/`, `permissions/`; без токена и audit) куда выбрал пользователь; «Импорт» открывает диалог «Открыть файл», проверяет схему, показывает превью/конфликты имён и сливает или заменяет. Так команды легко переносить на другой ПК и делиться ими с другими людьми; импортированные команды проходят ту же политику ПК (опасное — с карточкой).

#### 3b.6. Опциональный 3D-персонаж («свой VTuber на компьютере»)

- **По умолчанию выключен.** Включается в настройках; при выключенном персонаже клиент не грузит 3D-движок и модели.
- **Ассеты — только готовые стандартные:** модели `.vrm` (VRoid Hub и аналоги, либо собственная модель из VRoid Studio), готовые анимации Mixamo/mocap, ретаргетинг на VRM-скелет. Ничего не моделируется и не анимируется вручную. Для каждого ассета фиксировать источник и лицензию (условия VRM-лицензии модели, Mixamo terms); в репозиторий/сборку класть только ассеты, чья лицензия это допускает, иначе — загрузка пользователем.
- **Шаг 0 — исследование (до любой реализации персонажа):** изучить Desktop Mate — поведение (в т.ч. реверс-инжиниринг, например https://github.com/morluto/rea, только ради идей), официальный сайт/GitHub, EULA/условия Steam и лицензии их моделей и анимаций. Если лицензия **явно** разрешает использование их моделей в стороннем приложении — можно взять их за основу; иначе подобрать готовые бесплатные `.vrm` и анимации (Mixamo/mocap), похожие по набору на Desktop Mate (idle, взгляд, сидение на окне, перетаскивание, речь). Итог: таблица «ассет — источник — автор — лицензия — можно ли распространять» в `character/LICENSES` и краткая запись в плане.
- **Персонаж по умолчанию:** выбирается по итогам шага 0 — модель, чья лицензия разрешает использование в приложении и распространение в составе сборки (VRM-лицензия: avatar use / redistribution / modification по необходимости); коммерческое использование не обязательно. Пользователь может заменить на свою.
- **Рендер:** WebGL в WebView (например three.js + `@pixiv/three-vrm`; выбор при реализации) в отдельном окне Tauri.
- **Поведение (идеи Desktop Mate, Steam app 3301060):** прозрачное окно поверх рабочего стола, always-on-top, click-through везде, кроме самого персонажа; idle-анимации; реакция на курсор (взгляд/поворот головы) и на окна (сидит на краю окна/панели задач — где платформа даёт геометрию окон); перетаскивание мышью; **lip-sync с TTS** (по амплитуде/визем-оценке аудиочанков); состояния `слушаю / думаю / говорю` синхронны с голосовым режимом; эмоции — из Mood §7.5 (если доступно), без влияния на права.
- **Своя реализация:** код Desktop Mate не копируется; модели/анимации/ассеты используются **только** при лицензии, явно это разрешающей (шаг 0). Реверс-инжиниринг — только для изучения поведения и идей.
- **Платформы — должно работать везде (универсальный способ или платформенный обход):** на Windows прозрачность/always-on-top/click-through нативны. На Linux X11 — через EWMH-хинты и input shape. На Wayland always-on-top и позиция окна не гарантированы протоколом: на KDE — KWin-правило/скрипт окна или layer-shell (`wlr-layer-shell`, поддерживается KWin), на GNOME (Mutter без layer-shell) — запуск окна персонажа через XWayland как обход; click-through — пустой input region. Выбранный механизм объявляется как capability, деградация (например, без always-on-top) видна пользователю, а не молча. Персонаж исключается из скриншотов Контура 4 (3b.7).
- **Матрица тестов персонажа:** Windows 10/11 (100% и 150% DPI, 2 монитора); CachyOS KDE Plasma Wayland + NVIDIA (машина владельца); GNOME Wayland; X11-сессия (GNOME или KDE). По каждой: прозрачность, always-on-top, click-through, перетаскивание, реакция на курсор, lip-sync, исключение из скриншота, FPS/CPU в простое, поведение над полноэкранным окном.
- **Производительность:** лимит FPS, пауза рендера при полноэкранном приложении/игре и на батарее, замер CPU/GPU в простое (блок Owyx).

#### 3b.7. Контуры локального управления ПК (по уровням)

1. **Контур 1 — Приложения и система:**
   - Автообнаружение программ: меню Пуск, реестр Windows, XDG `.desktop` и `PATH` на Linux; пользовательские алиасы; запуск, штатное закрытие и перезапуск.
   - Список окон, фокус, сворачивание/разворачивание/закрытие; громкость и медиа (MPRIS / Windows Media Session); буфер обмена с разрешения, системные уведомления, таймеры.
2. **Контур 2 — Браузер и поиск:**
   - Открытие сайтов, вкладок, локальных документов и готовых поисковых запросов в браузере пользователя.
   - Опциональная автоматизация страницы: поиск, формы, переходы и клики через браузерный мост/CDP либо системный UI. Не публиковать CDP наружу и не предоставлять серверу произвольный доступ к профилям/куки браузера.
3. **Контур 3 — Консоль и файловая система (Grok Bot CLI-режим):**
   - Команды в `PowerShell` / `cmd` на Windows, `bash` / `zsh` на Linux с возвратом `stdout`, `stderr`, кода возврата и соблюдением таймаута.
   - Чтение, поиск по имени/содержимому, создание, перемещение и редактирование файлов/папок только в разрешённых директориях пользователя.
4. **Контур 4 — Экран и GUI Computer-Use:**
   - Скриншот экрана, выбранного монитора или окна с **исключением собственных окон** (оверлей, карточки, персонаж — флагом исключения из захвата, где ОС умеет, иначе временным скрытием на время снимка), чтобы модель не кликала сама в себя; **нормализация координат** под DPI/скейлинг (125%/150%) и несколько мониторов.
   - Мышь и клавиатура: движение, клики, скролл, drag-and-drop, текст и хоткеи через Win32 (`SendInput`, захват — DXGI Desktop Duplication / Windows Graphics Capture) на Windows, X11 либо разрешённую portal/libei-сессию на Wayland.
   - Доступность функций объявлять по фактической ОС/сессии и разрешениям: Wayland не гарантирует произвольный список/фокус окон, always-on-top и глобальный ввод. Проверить KDE Wayland, X11 и Windows отдельно; отсутствие backend/разрешения показывать как недоступную capability, без скрытого обхода. Опорные контракты: [ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) и [GlobalShortcuts portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html).

#### 3b.8. Техническая архитектура `server` ↔ `client` (`host bridge`)

- В Rust-бэкенде Tauri 2 работает локальный исполнитель — **`host bridge`**; он проверяет политику и исполняет типизированные действия, но не оркестрирует LLM.
- Подключение по HTTPS/WSS с авторизацией по токену. **Capabilities handshake:** при подключении и при каждом изменении тумблеров клиент передаёт манифест `client capabilities`: ОС/сессия (`windows` / `linux-wayland` / `linux-x11`), версия клиента/протокола, аудио-возможности, доступные инструменты и разрешённые контуры. Сервер подмешивает в список инструментов brain **только** объявленные `client.*` (выключен Контур 3 — нет `client.shell_exec`): экономия токенов и никаких пустых попыток. Локальные разрешения могут только сужать серверные права.
- Серверный `brain` отправляет `client_tool_call` только в явно выбранный активный клиент текущей авторизованной private owner/session. Привязка включает устройство; Discord/Telegram и другие общие чаты не получают управление ПК из факта присутствия пользователя. Результаты локальных действий не попадают в общую память/диалог автоматически (§12).
- **Несколько ПК одновременно:** к одному серверу может быть подключено несколько клиентов. У каждого устойчивый `device_id` (генерируется при первом запуске, имя ПК редактируется) и свой манифест capabilities. Сервер маршрутизирует `client.*` только на конкретное устройство: явно указанное пользователем («на ноутбуке…»), иначе — устройство, с которого пришёл ход; при неоднозначности спрашивает. Пользовательские быстрые команды маршрутизируются только в рамках сессии того клиента, который их объявил. В UI — выбор устройства и список подключённых ПК с их capabilities; отзыв устройства на сервере.
- Клиент повторно проверяет локальную политику, при необходимости показывает подтверждение и возвращает `client_tool_result`: статус, ограниченные `stdout`/`stderr`, код возврата, окна или скриншот. Скриншоты/вывод отправляются только в рамках разрешённого вызова; audit не сохраняет секреты и полное содержимое по умолчанию.
- Протокол: `call_id`, owner/session/device, версия схемы, deadline, отмена, ограничение размера результата и защита от повторного исполнения после reconnect. При disconnect, отзыве разрешения или блокировке сессии прекращать активные действия и отклонять устаревшие вызовы; не повторять их автоматически.
- Клиент не хранит серверную SQLite/Chroma и не вызывает LLM/STT/TTS напрямую (локален только детектор wake word). Новые API/WS-контракты (client tools, голосовая сессия, быстрые команды) реализовать и тестировать отдельно, не считать расширением проверенного chat streaming (§4/§5).
- Многошаговые задачи на ПК — через ограниченный серверный Agent loop (§10: лимит итераций, бюджет, условие «готово»), без переноса планирования в клиент.

#### 3b.9. Безопасность, приватность и контроль пользователя

- **Мастер-переключатель** «Разрешить Нейре управлять этим ПК» при первом запуске предлагается мастером настройки и **выключен до явного согласия**; независимые тумблеры четырёх контуров. Выключенные инструменты блокируются в Rust и не объявляются серверу; изменение разрешений обновляет capabilities и отзывает ожидающие/активные вызовы.
- **Профиль по умолчанию после включения (решение владельца): «безопасное — сама, опасное — спрашивает».** Режимы по контуру/риску: `Выключено`; `С подтверждением` (карточка `Разрешить / Отклонить` с конкретной командой/путём/действием и таймером автоотказа); `Автоматически для безопасных действий`. Безопасные по умолчанию: открыть разрешённую программу/ссылку/поиск, громкость/медиа, список окон, фокус, чтение в разрешённых папках. Опасные (всегда карточка, если владелец явно не изменил): произвольная CLI-команда, запись/удаление/перемещение файлов, закрытие программ с несохранёнными данными, ввод текста/клики в чужих окнах, отправка форм, всё за пределами allowlist. Сервер и содержимое страницы/файла не могут расширить разрешения; подтверждение привязано к конкретным параметрам вызова.
- **Secret redaction / deny-list:** разрешённые корни FS плюс deny-list для `.env`, `.ssh`, keychains, профилей/куки браузеров, хранилищ ключей; исключение — только отдельной карточкой на конкретный файл. Проверять нормализованный конечный путь, включая symlink/junction; shell и браузерный мост не должны обходить политику файлового инструмента. Произвольная CLI-команда не считается безопасной по одному deny-list. Вывод терминала/файлов перед отправкой проходит redaction известных форм секретов.
- **Индикация активности:** пока работают Контуры 3–4 или идёт захват экрана, заметный индикатор «Нейра управляет ПК» (рамка/бейдж оверлея, значок трея, персонаж в соответствующем состоянии).
- **Stop:** кнопка в UI/оверлее/трее и глобальный хоткей (с проверкой доступности на платформе; при недоступности — видимая кнопка). Отменяет активный вызов, прекращает ввод, завершает управляемое дерево дочерних процессов и прерывает TTS. Выполненные внешние действия автоматически не откатываются. Полный GUI/CLI-контур не включать до проверки отмены, подтверждений и завершения процессов.
- **Аудит:** локальный журнал действий (что, когда, по чьему запросу, решение пользователя, результат) с хранением **30 дней по умолчанию** (настраивается) и лимитом размера; серверный след — в `model_trace` хода без секретов.
- Обновления/перезапуск не должны молча расширять разрешения.

#### 3b.10. Хранение данных

В сборку клиента входят UI, стили, иконки, шрифты, звуки, Rust-модули `host bridge`, 3D-рантайм и (если лицензия позволяет) ассеты персонажа по умолчанию. Сервер отдаёт чат/историю, память, серверные конфиги, промпты, модули, логи, статус и голос через API с существующими ролями.

**Правило:** на сервере лежит только серверное (серверные конфиги, память, `fast_path`, логи сервера). Всё пользовательское — локально у клиента в папке **`Neyra`** в «Документах», создаётся при первом запуске:

- **Windows:** Known Folder `FOLDERID_Documents` (`SHGetKnownFolderPath`; учитывает перенос «Документов» и OneDrive), т.е. `…\Documents\Neyra`.
- **Linux:** `XDG_DOCUMENTS_DIR` через `xdg-user-dir DOCUMENTS` / `~/.config/user-dirs.dirs`; если не задан — `~/Documents`, если его нет — `~/.local/share/neyra` (`$XDG_DATA_HOME/neyra`). Выбранный путь показывается в настройках, его можно сменить.
- **Структура:** `settings/` (настройки приложения, голос, хоткеи, тема, окна/оверлей/персонаж), `commands/` (быстрые команды), `permissions/` (разрешения ПК, allowlist/deny-list), `logs/` (локальные логи клиента с ротацией), `audit/` (журнал действий на ПК, 30 дней по умолчанию), `character/` (выбранные `.vrm`, анимации, файл лицензий), `models/` (зарезервировано), `wakeword/` (локальная модель wake word «Нейра» и `wakeword.json` с источником и лицензией), `cache/` (кэш статуса). Формат — YAML/JSON со `schema_version` и миграциями; обновление клиента не затирает папку.
- **OneDrive/облачная синхронизация «Документов»** допустима, особой обработки нет; запись атомарная (временный файл + rename) с повтором при временной блокировке файла синхронизатором.
- **Не в папке:** токен — только в системном хранилище секретов (Credential Manager / Secret Service / KWallet), не в «Документах». В логах и audit — без секретов.

Это не реплика серверной памяти. URL сервера — из настроек, в том числе публичный домен §4; frp/прокси не входят в §3b.

- [ ] **Графика до инициализации WebView:** Linux-only выбор `auto / wayland / x11 / compatibility`, сохранение ручного режима восстановления вне пакета. Не отключать ускорение всем. Отключение DMABUF устраняло серое окно, но замедляло интерфейс: оставить его совместимым режимом восстановления, а не общей политикой. Настройки применять до GTK/WebView; учитывать явные пользовательские overrides.
- [ ] **Библиотеки готового пакета:** сравнивать bundled и system WebKit/GTK на одном release executable. В Owyx на указанной машине измерено примерно 30 против 60 FPS; для Нейры это гипотеза до собственного замера. Предусмотреть необязательный system runtime с проверкой зависимостей, понятной диагностикой и fallback к bundled. Выбор библиотек не должен скрыто менять Wayland/X11; отдельные сборки под каждый дистрибутив заранее не требуются.
- [ ] **Окружение дочерних процессов:** все запускаемые `host bridge` CLI, браузер, терминал и sidecar не наследуют AppImage-пути библиотек/GTK-модулей и служебные маркеры. Восстанавливать исходное окружение, различая отсутствующий, явно пустой и пользовательский `LD_LIBRARY_PATH`; проверить sync/async запуск. Путь исходного AppImage нужен родительскому updater, но не должен загрязнять окружение дочерних программ.

## 4. Серверная поставка и модульная эксплуатация

### Канон публикации

```text
Клиент / браузер
  → https://neyra.owyx.site  (+ wss://…/api/v1/ws/chat)
  → nginx/Caddy на VPS (TLS)
  → frps (HTTP vhost)
  → frpc на домашнем сервере
  → Control API 127.0.0.1:8787
```

Серверные данные (память, `.env`, серверные логи, модели) остаются на **домашнем** сервере; на VPS только proxy + frps. Docker Compose на VPS — запасной стенд, не замена канону. Bind по умолчанию loopback; наружу только через frp. Токены обязательны при внешнем доступе. IP/rate-limit/setup-guard — в security-model / reverse-proxy docs (не дублировать здесь).

Пример `frpc` (секреты не в git): `type=http`, `localPort=8787`, `customDomains=["neyra.owyx.site"]`; `api.public_base_url` + `api.public_path_prefix: /api`.

Планируемый `host bridge` §3b использует исходящее подключение клиента через этот защищённый маршрут, без открытого порта управления на ПК. До реализации определить отдельные роли/доступ к устройству, схемы `client_tool_call/result`, capabilities, отмену и version negotiation; проверить WSS через reverse proxy, disconnect/reconnect и несколько клиентов. Чатовый WSS-smoke ниже не подтверждает эти новые контракты.

- **Person card:** opaque `person_id` (по умолчанию `uuid5(platform:platform_user_id)`), `accounts[]` (`platform`, `platform_user_id`, `handle`, `display_name`, `avatar_url?`), `aliases[]`, free-form `facts[]`.
- **Нет** полей профиля first_name / last_name / birth_date / city — только факты из текста.
- **Speaker resolve:** только `platform + platform_user_id` → create+bind. Совпадение handle → merge proposal (админ), не auto-bind. Fuzzy/stem/display_name запрещены.
- **Mentions в тексте:** exact / word-boundary + явный список падежных окончаний (не «Максим»→«макс»).
- **Обращение:** nick / display_name; реальное имя — только если есть факт.
- **Diary:** от первого лица Нейры (чувства). **Journal:** хроника / reflection.
- **Merge:** LLM-tool `propose_people_merge` (pending); apply/reject в дашборде; undo из snapshot (`undone_at`).
- **Wipe API / dashboard:** scopes обязательны + `confirm: "WIPE"`; `sqlite3.backup` (+ Chroma при `ltm`); `server/data/**` в gitignore.
- **Не в этом PR:** суточный embedding-similarity job для кандидатов (memory consolidation) — отдельно после стабилизации proposals UI.

## 7.5. Mood & Relations (серверный MVP реализован локально, live-приёмка открыта)

Текущий MVP сохраняет настроение Нейры и отношения по person_id. Пока это ограниченные правила по явным фразам, не полноценный анализ диалога; дальнейшее развитие запланировано ниже. Diary/emotional_layer не заменяют mood/relations.

### Mood (настроение Нейры) — глобальное + краткосрочное

```text
neyra_mood:
  valence:   -1.0 … +1.0   # плохо → хорошо
  arousal:   0.0 … 1.0     # спокойствие → возбуждение
  label:     "спокойная" | "раздражённая" | "игривая" | …
  updated_at
  decay_half_life_hours: 8
```

В текущем MVP явные сигналы благодарности, извинения, оскорбления и признания лжи дают ограниченные изменения; обычная реплика сама по себе не меняет настроение. Полупериод возврата к нейтрали — 8 часов.

Как влияет: ограниченный блок данных о состоянии для brain и talk, отдельно от нейтральных system-инструкций по §12. Persona остаётся сильнее mood и поступает только в talk; brain использует состояние для планирования, не задаёт стиль персонажа. Опциональные voice/reactions — позже. Это состояние Нейры, не привязанное к человеку.

### Relationship — per `person_id`

```text
person_relation:
  person_id
  affinity:   -1.0 … +1.0
  trust:      0.0 … 1.0
  familiarity: 0.0 … 1.0
  tone_bias:  "cold" | "neutral" | "warm"
  last_significant_event
  history[]   # короткие записи
```

Таблица `person_relations` в общей SQLite. Симпатия меняется по явным сигналам, доверие снижается только при явном признании лжи, знакомство растёт после успешного хода. Полупериод decay — 30 дней, доверие возвращается к 0.50. Контекстный анализ, суточные LLM-summary и person↔person ещё не реализованы.

### Стык с Memory v2

```text
Global: neyra_mood  ← все ответы
Per person: person_relation + facts + accounts
diary (чувства) + journal + emotional_layer после хода
```

После успешной пары реплик: ограниченные сигналы → Δmood/Δrelation автора; `memory.diary_after_turn` запускает отдельную фоновую запись дневника. Опциональные WM/emotional LTM metadata работают отдельно и не являются вторым планировщиком diary. Mood/relation доступны следующему ходу; decay учитывает прошедшее время при чтении/ходе, без обязательного daily cron.

Ограничения: persona сильнее mood/relation; даже при affinity=−1 без токсичности вне persona; дашборд: настроение + отношение + reset; LLM не пишет affinity напрямую без лимитов (propose Δ / rules); wipe scopes: `mood` / `relations`.

## 10. Agent loop: качество ответов и фоновая память (только план)

Идея: вместо одного большого вызова модели Нейра для сложных задач работает в цикле: сама строит следующий шаг, проверяет результат и решает, готово ли. Цикл улучшает качество, а не скорость (каждая итерация это ещё один вызов модели), поэтому через него идёт не всё.

### Слои

- **Роутер на входе.** Простые реплики отвечаются сразу одним вызовом, сложные (многошаговые, с поиском, с инструментами) уходят в цикл. Задержка на коротких сообщениях не растёт.
- **Цикл для сложного.** План, затем шаги, затем самопроверка и ответ. Лимиты: максимум итераций, бюджет токенов, явное условие остановки. Шаги цикла публикуются в Event Bus и видны в дашборде.
- **Подтягивание контекста.** Перед ответом цикл сам решает, что достать из Memory Hub (точечный retrieval), а не грузит всё подряд.
- **Фоновая память.** После диалога отдельный проход без спешки решает, что запомнить, сжимает и сливает дубли, помечает устаревшее. Пользователь его не ждёт. Стыкуется с §7 Memory v2.

### Не сейчас

- Реализация до стабилизации §7 и §7.5.
- Сложные мультиагентные схемы.

### Готово, когда (только план)

Смена persona/model/provider/режима/флагов, сокращение STM, reset/wipe и рестарт инвалидируют цепочку. Весь ход одной беседы сериализован между event loops. Unknown parent/overflow восстанавливают persona и ограниченный публичный replay без повторного brain/tools; rewrite/empty retry не закрепляют отброшенные ответы. После публичного текста replay запрещён.
- Provider chains не сохраняются на диск. Удаление response ID ограничено по времени/очереди и выполняется best effort исходным подключением; удаления provider backups это не гарантирует. Response ID не считается request ID. Меньший payload не доказывает меньший billing; TTL, compaction и межключевую изоляцию проверяет пользователь отдельно.

## 13. Переработка памяти и её интерфейса (после аудита §12)

Целевая схема раздела «Память»:

- **Короткая:** текущий контекст чата, который получает модель. Показывать фактическую историю/состав контекста; это не вся долговременная база и не скрытые рассуждения модели.
- **Промежуточная:** личный дневник Нейры, автоматически формируемый после каждой завершённой пары «сообщение пользователя + ответ Нейры». Записи от первого лица Нейры, без внешнего рассказчика и выдуманных событий.
- **Долгая:** устойчивые сведения, отобранные после рефлексии и сохранённые в долгосрочную память. Показывать понятные записи, их происхождение и актуальность.

Локально реализовано в PR #27: STM — ограниченные окна процесса по owner/channel; diary — SQLite с владельцем/каналом; долгая память — факты профилей с источником. Старые записи не переписываются и не приписываются произвольному пользователю. Семантический retrieval сохранён, просмотр фактов не является полным экспортом Chroma.

- [x] **Журнал ядра:** System → «События памяти», только просмотр, обновление и admin delete/clear; без ручной формы.
- [x] **Дневник:** ручная форма убрана; запись от первого лица автоматически после завершённой пары. Новые источники запрашивают первое лицо; исторические записи сохранены. Соблюдение инструкции моделью — live-критерий. Канонический планировщик — `memory.diary_after_turn`; устаревшие diary-настройки не создают второй поток записей.
- [x] **Очистка и вайпы:** существующие API, роли, подтверждения и кнопки сохранены; отложенные jobs после wipe не восстанавливают удалённое; регрессии прав/удаления и browser-сценарий удаления журнала.
- [x] **Поиск RAG:** техническая форма убрана; долгая память показывает факты/источник, исправления остаются в «Людях». Retrieval Нейры не отключён.
- [x] **Локальная приёмка:** три секции, отдельный журнал, empty/error/retry, клавиатура, обе темы и desktop/mobile; браузер получает действительные данные временного backend, не только mocks HTTP.
