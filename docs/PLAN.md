## 2. Что уже работает

### 2.1. Основа

Этапы 1a–1d и 2 завершены: аудит, перенос server/client/devtools, слои конфигурации, роли LLM-провайдеров и единый Control API. Их подробные чеклисты и старые прогоны удалены из рабочего плана; история остаётся в Git и [VERSION.md](VERSION.md).

- `server/core/` — ядро, API, память и общие сервисы; `server/modules/` — интеграции; `server/dashboard/` — серверная ops-панель.
- `client/src-tauri` — Rust-часть десктопа (Tauri 2, IPC); UI находится в `client/src`.
- `devtools/mcp_server/` — только разработка, не runtime-поставка.
- Бизнес-логика, память, LLM/STT/TTS, оркестрация инструментов и Event Bus остаются на сервере. Локальные OS-операции на ПК пользователя исполняет опциональный `host bridge` клиента (§7.6).
- Control API — `server/core/api/`, не отдельный модуль. Loopback по умолчанию; внешний доступ требует auth/ролей. Модули взаимодействуют через API и Event Bus.
- Секреты — `server/.env`; память — `server/data/` либо настроенный `paths.data_dir` / `NEYRA_DATA_DIR`. Конфиги, persona, память, модели и логи не включаются в коммит и не затираются при обновлении.

### 2.2. Сервер, панель и память

Серверная реализация, dashboard и исправления pipeline установлены на MiniPC; открыта live-приёмка моделей и интеграций (§8.1).

- **Ops-панель:** статус, модули, память, система, вебхуки, настройки, доступ, документация; обе темы, клавиатура, desktop/mobile.
- **Модули в вебе:** действия по `lifecycle` (resident → PATCH enabled с авто soft-restart ядра; on_demand → invoke; общий enable/config). В дашборде модуля — вкладки «Управление / Конфиги / Логи», загрузка `.zip` (`POST /v1/plugins/upload`), удаление (`discord` защищён), правка конфиг-файлов (`/v1/plugins/{id}/files`), хвост логов (`/v1/logs`).
- **Память v2 (people / diary / journal):** account-first модель людей без анкетных полей, `person_id = uuid5(platform:platform_user_id)`, `accounts[]`, `aliases[]`, свободные `facts[]`. Speaker resolve только по `platform + platform_user_id`; совпадение handle даёт merge proposal, а не auto-bind. Diary — от первого лица Нейры, journal — хроника/reflection. Merge — LLM-tool `propose_people_merge` (pending), apply/reject в дашборде, undo из snapshot. Wipe — только с явными scopes и `confirm: "WIPE"`, с `sqlite3.backup` (и Chroma при `ltm`).
- **Mood & Relations (MVP):** `neyra_mood` (valence/arousal/label, decay 8 ч) и `person_relations` (affinity/trust/familiarity, decay 30 дней). Меняются по явным сигналам после успешного хода, попадают в `turn_prep` для brain и talk; persona сильнее состояния и идёт только в talk. Развитие — §8.5.
- **Память в интерфейсе:** три раздела (короткая / дневник / долгая), отдельный журнал «События памяти», очистка и вайпы с подтверждением, факты и источник в «Людях».
- **Тексты и промпты:** system-инструкции и основа локализации вынесены в `server/resources/`; persona остаётся отдельным файлом. Остаток — §8.6.

## 3. Правила проекта и качество

### 3.1. Постоянные правила

- Изменение `core/` должно быть обосновано задачей, которую нельзя закрыть модулем или существующим API.
- Конфигурация: `server/config.yaml` + тематические `server/config/*.yaml` и конфиги модулей; источники типов/defaults — tracked examples и schema. Роли моделей задаются через `llm.*_model` и `llm.providers.*`, без привязки к одной постоянной модели.
- Общие инструкции: `docs/en/` и `docs/ru/`. Рабочие задачи — здесь, история поставок — в VERSION.
- Клиент не оркестрирует агента и не хранит серверную память. Локальные права могут только сужать серверные.

### 3.2. Что проверяем на каждом этапе

- Python compileall и unit/integration tests для затронутых серверных частей.
- API auth/role tests, config schema tests, migration dry-run и data preservation check.
- Dev MCP compile и import smoke: из `devtools/mcp_server/` выполнить `python -m compileall -q server.py` и `python -c "import server; assert server.mcp.name == 'neyra-mcp-debug'"`. Import smoke проверяет регистрацию MCP app и не обращается к Control API или секретам.
- Security boundary: localhost default, explicit LAN bind, token roles, audit и отсутствие секретов в логах.
- Тестовая матрица: Windows/Linux client/server unavailable, incompatible API version, stream reconnect, module failure и rollback config. Для `host bridge` (§7.6): opt-in/отзыв, private owner/session/device isolation, повторы `call_id`, просроченный вызов, disconnect/Stop, лимиты вывода, секреты в audit и окружение дочерних процессов. Release-матрица Win32/X11/KDE Wayland + NVIDIA; облачные проверки не заменяют реальные ОС/GPU.
- Клиент: `tsc -b`, `eslint --max-warnings 0`, Vitest, Rust fmt/clippy/test — на Node 22 и актуальном toolchain.

### 4.2. Приёмка реформы (не только текущего PR)

**Приёмка — это приёмка реформы целиком, а не только исправлений этого PR.** Проверяется всё новое, что появляется в ветке: и приложение, и сайт v2, и их совместная работа с ядром. Каждый этап (P0–P6 веба, шаги десктопа) принимается отдельно, но итоговая приёмка ставится один раз — по всей реформе, на одном срезе HEAD.

**A. Приложение (десктоп).** CI и headless-прогоны не подтверждают работу на реальной системе:

- **Linux (CachyOS, KDE Plasma Wayland + NVIDIA):** AppImage и `.deb`; запуск, окно и трей, OS keyring без plaintext, микрофон/PTT/Stop, **быстрый тап и двойной тап PTT** (нажал и отпустил, пока открывается микрофон — захват должен закрыться, а не висеть до лимита; при втором нажатии в это же окно первый захват закрывается, второй стартует после), **CTRL+ALT+SPACE при открытом окне** (второй захват не стартует, кнопка продолжает работать), озвучка и смена устройства вывода, **появление сообщения о fallback на системное устройство**, reconnect после обрыва, переключение тредов с историей, приватный чат, wake word на обученной модели.
- **Windows (VM):** NSIS `setup.exe` (currentUser), WebView2, keyring, автообновление N → N+1, тот же набор (Stop, reconnect, история, треды), путь с пробелами и кириллицей, завершение дочерних процессов.

**B. Сайт v2 (после этапов P0–P6).** Отдельный чек-лист по спеке `web-v2.md`, не подменяется проверкой приложения:

- вход и роли (`admin` / `user`), регистрация и инвайты, разграничение видимости моделей;
- чат: стриминг, смена модели по ходу, дерево веток, вложения, `stop`, инструменты и размышления в ленте;
- память: свои факты, правка админом, дневник и LTM только для админа, поиск и экспорт;
- история: поиск, pin, папки, архив, экспорт MD/JSON/PDF, шаринг только для вошедших;
- админка: пользователи, retention, провайдеры, ops-раздел и `/legacy` на время миграции;
- мобильная и десктопная вёрстка в браузере, поведение при обрыве сети и повторном входе.

**C. Совместная работа и ядро.** Требования контракта из §15 спеки: identity веб-пользователя в памяти ядра (один `person_id`, а не два), вложения через `attachments[]`, `model` в запросе, событие `stop` в WS; `X-Neyra-Identity` не принимается без валидного JWT; `/v1/desktop/*` доступен только с Bearer-ролью admin.

**D. Сервер и эксплуатация.** Живые `/health` и `/health/ready` (включая деградацию при 429), WSS через прокси, поведение при 503 и обрыве, бэкап и восстановление, отсутствие плейнтекстовых секретов.

**E. Релиз.** Подписанный N → N+1 на тестовом ключе, отклонение повреждённого артефакта, установка с нуля и обновление поверх, сохранение профиля, темы и keyring.

**Правила приёмки:** порядок — **сайт v2 → приложение (Linux, затем Windows) → совместные сценарии → релиз**; чек-лист ведётся в PR; каждый пункт — факт запуска с версией пакета и SHA, а не «собралось»; провал любого пункта возвращает этап в работу, частичная приёмка не закрывает реформу.

## 7. Этап 4 (после сайта): десктоп до целевого объёма

Работа этого этапа и аппаратная приёмка приложения начинаются **после** сайта v2 (решение владельца 12.11.2026).

Клиент — **Tauri 2 + React + TypeScript (Rust backend + WebView UI)** для Windows, Linux и macOS. Фронт — `desktop` на общем ките (§5); Rust-часть и IPC остаются в `client/src-tauri`.

Windows остаётся минимумом защиты из §0. Linux (CachyOS KDE Wayland + NVIDIA у владельца) и Windows по решению владельца 2026-10-31 поддерживаются **на равных**; native computer use также доступен на macOS. Ниже — целевая функциональность (ТЗ), а не уже доступные возможности.

### 7.1. Продуктовое видение

Нейра на ПК — **глобальный ИИ-ассистент на компьютере пользователя**. Он собран из четырёх идей, но реализован по-своему:

| Источник идеи | Что берём |
| --- | --- |
| **Grok Bot** | Умный агент с опциональным управлением ПК: CLI/FS, браузер, GUI, многошаговые задачи с проверкой результата. |
| **ChatGPT live voice** | Голосовой режим «просто разговариваем»: непрерывный диалог, перебивание (barge-in), естественные паузы, без кнопок на каждую реплику. |
| **JARVIS** | Быстрые команды: короткая фраза или хоткей сразу запускают заранее описанное действие без долгих рассуждений LLM. |
| **Desktop Mate** | Опциональный 3D-персонаж поверх рабочего стола («свой VTuber на компьютере»). |

«Мозг» (LLM, память, рассуждения, выбор шагов), **STT и TTS** живут на сервере (`server/core/`, MiniPC). `desktop` — «лицо», уши/рот (захват микрофона, проигрывание звука), `client/src-tauri` — опциональные «руки» Нейры на машине пользователя. Это отдельная поверхность исполнения, **не** серверный workspace (§11.2).

С Нейрой одинаково удобно общаться **голосом и текстом**; текстовый и голосовой ход проходят один и тот же серверный pipeline и общую историю private-сессии.

### 7.2. Решения владельца (2026-10-31)

- 3D-персонаж есть, но **выключен по умолчанию**; включается в настройках.
- Голос и текст — равноправные способы общения.
- Активация голосом — несколько режимов на выбор: по умолчанию wake word **«Нейра»** + команда; режим «слушать всегда»; push-to-talk (хоткей/кнопка).
- STT и TTS выполняются **на сервере**; клиент только захватывает/стримит микрофон и проигрывает аудио.
- Полная реализация TTS+STT (голосовой модуль) идёт **вместе с десктоп-приложением**, а не после ВКР.
- Права на ПК по умолчанию: **безопасное делает сама, перед опасным спрашивает** (карточка `Разрешить / Отклонить`).
- Быстрые команды создаются тремя способами: интерфейс, голос («запомни команду…»), конфиг.
- К защите ВКР владелец хочет **всё**, включая персонажа (§0 при этом не меняется; см. §7.9).

### 7.3. Экраны и окна клиента

1. **Подключение:** адрес сервера и токен; хранение в Windows Credential Manager и системном хранилище Linux (Secret Service / KWallet), не открытым текстом. Проверка совместимости версии API.
2. **Чат:** server-side history, streaming, вложения, озвучка ответа (кнопка/авто), индикатор моделей хода.
3. **Голос (live-режим):** полноэкранный/компактный режим разговора без текста — визуализация уровня микрофона и речи Нейры, статус `слушаю / думаю / говорю`, кнопки «пауза микрофона» и «завершить разговор».
4. **Статус:** health, modules, models, API version (экран «Статус», не «Дашборд»).
5. **Модули:** список, состояние, enable/disable, start/stop, мягкий рестарт по существующим API/ролям.
6. **Быстрые команды:** список, создание/редактирование, тест-запуск, импорт/экспорт (§7.5, хранение — §7.8).
7. **Доступ к ПК:** мастер-тумблер, контуры, режимы, allowlist/deny-list, журнал действий (§7.6–§7.7).
8. **Персонаж:** вкл/выкл, выбор `.vrm`, размер/позиция/монитор, набор анимаций, реакции, производительность (§7.5).

### 7.4. Голосовой модуль: STT, TTS и live voice

Серверная основа переиспользуется: `server/core/voice/` (`stt.py`, `tts.py`, `deepgram_tts.py`, `yandex_tts.py`, `config.py`), конфиг `server/config/voice.yaml` (пример `voice.example.yaml`: STT lanes `local` faster-whisper / `cloud` deepgram/openrouter/groq; основной облачный TTS — Deepgram с fallback на Yandex при ошибке или отсутствии ключа), `server/scripts/voice_preflight.py`. Модуль `server/modules/local_voice/` пока заглушка (`enabled: false`); голосовой цикл ПК-клиента живёт на сервере как сервис ядра/API. Discord-голос (§11.4) — отдельный контур, не блокирует и не блокируется.

- **Транспорт:** отдельный WSS-канал голосовой сессии (не расширение проверенного chat streaming): клиент стримит PCM/Opus-фреймы микрофона, сервер возвращает частичные/финальные транскрипты, события хода и аудиочанки TTS. Версия схемы, `session_id`, отмена, лимиты размера и длительности.
- **STT на сервере:** потоковое распознавание (streaming, где провайдер умеет; иначе сегменты по VAD), частичные гипотезы для UI, язык из `voice.language`. Провайдеры и fallback — через существующие lanes `voice.stt`. Сейчас провайдеры не дают partial: сервер честно объявляет `partial_transcripts: false`, `streaming_stt: false`.
- **TTS на сервере:** потоковая озвучка по предложениям, чтобы первая фраза звучала до конца генерации ответа; формат и частота согласуются в handshake; клиент буферизует и проигрывает. Ответ для голоса — простой текст без Markdown.
- **Режимы активации** (выбор в настройках, по умолчанию wake word):
  1. **Wake word «Нейра» + команда.** Детектор работает **локально на ПК пользователя**: звук не уходит на сервер, пока слово не распознано; после срабатывания фраза-команда стримится в серверный STT. Детектор должен быть **лёгким**: **openWakeWord** (Apache-2.0) с собственной моделью «Нейра», обученной на синтетических данных (TTS-генерированные произношения + шум/негативы), без записи голоса владельца. Porcupine рассмотрен и отклонён: коммерческая лицензия и ключ доступа. Бюджет: ≤ ~2–3% одного ядра CPU и ≤ ~50–100 МБ RAM в режиме ожидания на среднем ноутбуке, без GPU; задержка срабатывания ≤ ~0,5 с. Детектор в отдельном потоке Rust, выключается вместе с микрофоном; ложные срабатывания на похожие слова и порог чувствительности настраиваются. Бюджет проверяется замером на обеих ОС (§7.11).
  2. **Слушать всегда:** клиентский VAD режет речь на фразы и отправляет только их; явный индикатор «микрофон активен» всё время.
  3. **Push-to-talk:** глобальный хоткей или кнопка в оверлее/трее; на Wayland — через GlobalShortcuts portal, при недоступности — видимая кнопка.
- **Live voice (идея ChatGPT voice mode):** непрерывный дуплексный диалог: VAD определяет конец реплики, Нейра отвечает голосом, пользователь может **перебить** (barge-in) — клиент гасит воспроизведение, сервер отменяет текущую генерацию/TTS и принимает новую реплику. AEC обязателен для дуплекса через колонки; пока его нет, по умолчанию честный half-duplex, а перебивание во время речи — явная опция «в наушниках». Короткие подтверждения («угу», «секунду») и честный статус при задержке провайдера (BUG-04).
- **Приватность:** микрофон включается только с явного разрешения; индикатор записи; аудио по умолчанию не сохраняется, в истории остаётся транскрипт. Голосовой ход не даёт больше прав, чем текстовый; опасные действия по-прежнему требуют карточки.

### 7.5. Быстрые команды, персонаж, контуры ПК

**Быстрые команды (JARVIS-контур).** Серверный `agent.fast_path` в `server/config/agent.yaml` (пример `agent.example.yaml`: regex-allowlist однозначных команд до brain, `enabled: false`, `intents[]`) **остаётся серверным** механизмом для серверных событий (умный дом и т.п.). **Пользовательские быстрые команды ПК в него не пишутся** и хранятся только локально у клиента (§7.8).

- **Модель команды:** `name`, триггеры (фразы/regex, хоткей), действие (`event_type` на сервере **или** `client_tool` с фиксированными параметрами, например «открой Steam», «режим работы» = набор приложений/окон/громкость), требуемый контур/уровень риска, нужно ли подтверждение, ответ голосом.
- **Исполнение:** совпадение триггера → действие без полного хода brain; неоднозначность → обычный ход LLM. Быстрая команда не может обойти локальную политику ПК.
- **Три способа создания** (одна схема, одно локальное хранилище `Neyra/commands/`): UI; голос/чат («запомни команду…» — сервер разбирает фразу и возвращает черновик, клиент сохраняет локально после подтверждения); файл `Documents/Neyra/commands/*.yaml` с hot-reload, валидацией схемы и показом ошибок (файл, строка, причина).
- **Синхронизация с сервером только в рантайме:** активные команды (имена, триггеры, тип действия, без секретов) клиент объявляет в capabilities handshake и обновляет при изменении; сервер держит их в памяти **сессии этого клиента** и **не сохраняет** на диск или в память Нейры.
- **Только из приложения:** пользовательские быстрые команды работают **только из десктоп-приложения** (голос/текст в клиенте). Из Discord, Telegram, dashboard и любых других каналов они недоступны независимо от того, включён ли ПК.
- **Экспорт/импорт:** «Экспорт» открывает нативный диалог «Сохранить как» (Tauri `@tauri-apps/plugin-dialog`) и сохраняет файл конфига (`settings/`, `commands/`, `permissions/`; без токена и audit) куда выбрал пользователь; «Импорт» открывает «Открыть файл», проверяет схему, показывает превью/конфликты имён и сливает или заменяет. Импортированные команды проходят ту же политику ПК.

**3D-персонаж («свой VTuber на компьютере»).**

- **По умолчанию выключен.** Включается в настройках; при выключенном персонаже клиент не грузит 3D-движок и модели.
- **Ассеты — только готовые стандартные:** модели `.vrm` (VRoid Hub и аналоги, либо собственная из VRoid Studio), готовые анимации Mixamo/mocap, ретаргетинг на VRM-скелет. Для каждого ассета фиксировать источник и лицензию; в репозиторий/сборку класть только ассеты, чья лицензия это допускает.
- **Шаг 0 — исследование (до любой реализации):** изучить Desktop Mate (поведение, реверс-инжиниринг только ради идей), EULA/условия Steam и лицензии моделей/анимаций. Итог: таблица «ассет — источник — автор — лицензия — можно ли распространять» в `client/character/LICENSES.md`. Результат шага 0: ассеты Desktop Mate не redistributable, рекомендуемый default — VRoid β AvatarSample_3 (CC0), бинарный `.vrm` в сборку не кладётся.
- **Рендер:** WebGL в WebView (three.js + `@pixiv/three-vrm`) в отдельном окне Tauri; прозрачное окно поверх рабочего стола, always-on-top, click-through везде, кроме персонажа.
- **Поведение:** idle-анимации; реакция на курсор (взгляд/поворот головы) и на окна; перетаскивание мышью; **lip-sync с TTS**; состояния `слушаю / думаю / говорю` синхронны с голосовым режимом; эмоции — из Mood (§8.5), без влияния на права.
- **Платформы:** Windows — нативно; Linux X11 — EWMH-хинты и input shape; Wayland — KWin-правило/layer-shell на KDE, XWayland-обход на GNOME, click-through через пустой input region. Выбранный механизм объявляется как capability, деградация видна пользователю, а не молча. Персонаж исключается из скриншотов Контура 4.
- **Матрица тестов:** Windows 10/11 (100% и 150% DPI, 2 монитора); CachyOS KDE Plasma Wayland + NVIDIA; GNOME Wayland; X11. По каждой: прозрачность, always-on-top, click-through, перетаскивание, реакция на курсор, lip-sync, исключение из скриншота, FPS/CPU в простое, поведение над полноэкранным окном.
- **Производительность:** лимит FPS, пауза рендера при полноэкранном приложении/игре и на батарее, замер CPU/GPU в простое.

**Контуры локального управления ПК (по уровням).**

1. **Контур 1 — Приложения и система:** автообнаружение программ (меню Пуск, реестр Windows, XDG `.desktop` и `PATH`), пользовательские алиасы, запуск/закрытие/перезапуск; список окон, фокус, сворачивание/разворачивание; громкость и медиа (MPRIS / Windows Media Session); буфер обмена с разрешения, системные уведомления, таймеры.
2. **Контур 2 — Браузер и поиск:** открытие сайтов, вкладок, локальных документов и поисковых запросов в браузере пользователя; опциональная автоматизация страницы (поиск, формы, переходы, клики) через браузерный мост/CDP либо системный UI. Не публиковать CDP наружу и не давать серверу произвольный доступ к профилям/куки.
3. **Контур 3 — Консоль и файловая система:** команды в `PowerShell`/`cmd` на Windows, `bash`/`zsh` на Linux с возвратом `stdout`, `stderr`, кода возврата и таймаутом; чтение, поиск, создание, перемещение и редактирование файлов только в разрешённых директориях.
4. **Контур 4 — Экран и GUI Computer-Use:** скриншот экрана/монитора/окна с **исключением собственных окон**; нормализация координат под DPI (125%/150%) и несколько мониторов; мышь и клавиатура через Win32 (`SendInput`, DXGI Desktop Duplication / Windows Graphics Capture), X11 либо разрешённую portal/libei-сессию на Wayland. Native accessibility на Windows и macOS: `client.computer_snapshot` отдаёт ограниченное JSON-дерево переднего окна с временными `ref` без значений редактируемых полей; `computer_click`/`computer_type`/`computer_press` работают по `ref`, ссылки устаревают после действия, нового снимка или 120 секунд, поля пароля исключены. На Linux эти четыре инструмента возвращают `unsupported_platform`.

Доступность функций объявлять по фактической ОС/сессии и разрешениям: Wayland не гарантирует произвольный список/фокус окон, always-on-top и глобальный ввод. Отсутствие backend/разрешения показывать как недоступную capability, без скрытого обхода. Опорные контракты: [ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) и [GlobalShortcuts portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html).

### 7.6. Техническая архитектура `server` ↔ `client` (`host bridge`)

- В Rust-бэкенде Tauri 2 работает локальный исполнитель — **`host bridge`**; он проверяет политику и исполняет типизированные действия, но не оркестрирует LLM.
- Подключение по HTTPS/WSS с авторизацией по токену. **Capabilities handshake:** при подключении и при каждом изменении тумблеров клиент передаёт манифест: ОС/сессия (`windows` / `macos` / `linux-wayland` / `linux-x11`), версия клиента/протокола, аудио-возможности, доступные инструменты и разрешённые контуры. Сервер подмешивает в список инструментов brain **только** объявленные `client.*`.
- Серверный `brain` отправляет `client_tool_call` только в явно выбранный активный клиент текущей авторизованной private owner/session. Привязка включает устройство; Discord/Telegram и другие общие чаты не получают управление ПК из факта присутствия пользователя. Результаты локальных действий не попадают в общую память автоматически.
- **Несколько ПК одновременно:** у каждого устойчивый `device_id` и свой манифест capabilities. Сервер маршрутизирует `client.*` только на конкретное устройство: явно указанное пользователем, иначе — устройство, с которого пришёл ход; при неоднозначности спрашивает. В UI — выбор устройства и список подключённых ПК с capabilities; отзыв устройства на сервере.
- Клиент повторно проверяет локальную политику, при необходимости показывает подтверждение и возвращает `client_tool_result`: статус, ограниченные `stdout`/`stderr`, код возврата, окна или скриншот. Скриншоты/вывод отправляются только в рамках разрешённого вызова; audit не сохраняет секреты и полное содержимое по умолчанию.
- Протокол: `call_id`, owner/session/device, версия схемы, deadline, отмена, ограничение размера результата и защита от повторного исполнения после reconnect. При disconnect, отзыве разрешения или блокировке сессии прекращать активные действия и отклонять устаревшие вызовы; не повторять их автоматически.
- Клиент не хранит серверную SQLite/Chroma и не вызывает LLM/STT/TTS напрямую (локален только детектор wake word). Новые API/WS-контракты (client tools, голосовая сессия, быстрые команды) реализуются и тестируются отдельно, не считаются расширением проверенного chat streaming.
- Многошаговые задачи на ПК — через ограниченный серверный Agent loop (§11.3: лимит итераций, бюджет, условие «готово»), без переноса планирования в клиент.

### 7.7. Безопасность, приватность и контроль пользователя

- **Мастер-переключатель** «Разрешить Нейре управлять этим ПК» при первом запуске предлагается мастером настройки и **выключен до явного согласия**; независимые тумблеры четырёх контуров. Выключенные инструменты блокируются в Rust и не объявляются серверу; изменение разрешений обновляет capabilities и отзывает ожидающие/активные вызовы.
- **Профиль по умолчанию после включения: «безопасное — сама, опасное — спрашивает».** Режимы по контуру/риску: `Выключено`; `С подтверждением` (карточка `Разрешить / Отклонить` с конкретной командой/путём/действием и таймером автоотказа); `Автоматически для безопасных действий`. Безопасные по умолчанию: открыть разрешённую программу/ссылку/поиск, громкость/медиа, список окон, фокус, чтение в разрешённых папках. Опасные (всегда карточка, если владелец явно не изменил): произвольная CLI-команда, запись/удаление/перемещение файлов, закрытие программ с несохранёнными данными, ввод текста/клики в чужих окнах, отправка форм, всё за пределами allowlist. Сервер и содержимое страницы/файла не могут расширить разрешения; подтверждение привязано к конкретным параметрам вызова.
- **Secret redaction / deny-list:** разрешённые корни FS плюс deny-list для `.env`, `.ssh`, keychains, профилей/куки браузеров, хранилищ ключей; исключение — только отдельной карточкой на конкретный файл. Проверять нормализованный конечный путь, включая symlink/junction; shell и браузерный мост не должны обходить политику файлового инструмента. Вывод терминала/файлов перед отправкой проходит redaction известных форм секретов.
- **Индикация активности:** пока работают Контуры 3–4 или идёт захват экрана, заметный индикатор «Нейра управляет ПК» (рамка/бейдж оверлея, значок трея, персонаж в соответствующем состоянии).
- **Stop:** кнопка в UI/оверлее/трее и глобальный хоткей (с проверкой доступности на платформе; при недоступности — видимая кнопка). Отменяет активный вызов, прекращает ввод, завершает управляемое дерево дочерних процессов и прерывает TTS. Выполненные внешние действия автоматически не откатываются. Полный GUI/CLI-контур не включать до проверки отмены, подтверждений и завершения процессов.
- **Аудит:** локальный журнал действий (что, когда, по чьему запросу, решение пользователя, результат) с хранением **30 дней по умолчанию** (настраивается) и лимитом размера; серверный след — в `model_trace` хода без секретов.
- Обновления/перезапуск не должны молча расширять разрешения.

### 7.8. Хранение данных клиента

В сборку клиента входят UI, стили, иконки, шрифты, звуки, Rust-модули `host bridge`, 3D-рантайм и (если лицензия позволяет) ассеты персонажа по умолчанию. Сервер отдаёт чат/историю, память, серверные конфиги, промпты, модули, логи, статус и голос через API с существующими ролями.

**Правило:** на сервере лежит только серверное (серверные конфиги, память, `fast_path`, логи сервера). Всё пользовательское — локально у клиента в папке **`Neyra`** в «Документах», создаётся при первом запуске:

- **Windows:** Known Folder `FOLDERID_Documents` (`SHGetKnownFolderPath`; учитывает перенос «Документов» и OneDrive), т.е. `…\Documents\Neyra`.
- **Linux:** `XDG_DOCUMENTS_DIR` через `xdg-user-dir DOCUMENTS` / `~/.config/user-dirs.dirs`; если не задан — `~/Documents`, если его нет — `~/.local/share/neyra` (`$XDG_DATA_HOME/neyra`). Выбранный путь показывается в настройках, его можно сменить.
- **Структура:** `settings/` (настройки приложения, голос, хоткеи, тема, окна/оверлей/персонаж), `commands/` (быстрые команды), `permissions/` (разрешения ПК, allowlist/deny-list), `logs/` (локальные логи клиента с ротацией), `audit/` (журнал действий на ПК, 30 дней по умолчанию), `character/` (выбранные `.vrm`, анимации, файл лицензий), `models/` (зарезервировано), `wakeword/` (локальная модель wake word «Нейра» и `wakeword.json` с источником и лицензией), `cache/` (кэш статуса). Формат — YAML/JSON со `schema_version` и миграциями; обновление клиента не затирает папку.
- **OneDrive/облачная синхронизация «Документов»** допустима, особой обработки нет; запись атомарная (временный файл + rename) с повтором при временной блокировке файла синхронизатором.
- **Не в папке:** токен — только в системном хранилище секретов (Credential Manager / Secret Service / KWallet), не в «Документах». В логах и audit — без секретов.

Это не реплика серверной памяти. URL сервера — из настроек, в том числе публичный домен (§9); frp/прокси не входят в этот этап.

### 7.9. Порядок реализации и текущий статус

Владелец хочет к защите ВКР **всё**, включая персонажа. §0 не меняется: его «Минимум к защите» остаётся обязательным ядром, а остальное — целевой объём, который реализуется по шагам так, чтобы в любой момент было что показать. Каждый шаг заканчивается рабочей сборкой Windows + Linux.

| Шаг | Содержание | Статус |
| --- | --- | --- |
| 1 | Каркас и минимум §0: `src-tauri`, подключение/токен, чат со streaming, Статус, Модули, трей, работа без сервера, NSIS и Linux-пакет, PR CI | код готов, приёмка на железе открыта (§4.2) |
| 2 | Голос v1: серверная голосовая WSS-сессия, push-to-talk, STT→ход→TTS, проигрывание и прерывание | готово, приёмка открыта |
| 3 | `host bridge v1` + безопасность: handshake, тумблеры, Контуры 1–2, карточки, Stop, аудит, индикатор | готово, приёмка открыта |
| 4 | Быстрые команды: локальное хранилище, экран, создание голосом и файлом, рантайм-синхронизация | код готов в ветке, приёмка открыта |
| 5 | Live voice и wake word: локальный детектор, «слушать всегда», VAD, barge-in, AEC | частично: AEC и обученная модель «Нейра» открыты |
| 6 | Контур 3 (CLI/FS) и Контур 4 (экран/мышь/клавиатура) для Windows и KDE Wayland/X11 | код готов в ветке, приёмка открыта |
| 7 | 3D-персонаж: шаг 0, окно-оверлей, VRM, анимации, реакции, lip-sync | шаг 0 закрыт, runtime в ветке, матрица тестов открыта |
| 8 | Полировка и релиз: автообновление N → N+1, Monaco/логи/import-export, release-приёмка | подпись и обновление готовы, прогон N → N+1 открыт |

Риск-план: если сроки поджимают, шаги 7 и 8 (часть Monaco) сдвигаются последними, но порядок 1→6 не меняется, а безопасность (шаг 3) не откладывается ради скорости.

**Открыто по шагу 5:** AEC не реализован — по умолчанию честный half-duplex, микрофон молчит, пока Нейра говорит (это не эхо-подавление); голосовое перебивание во время речи — явная опция «в наушниках». Модель «Нейра» не обучена и не поставляется: обучение openWakeWord на синтетике, замер ложных срабатываний и бюджета CPU/RAM открыты. Замер на VM CI-класса: ≤ ~2,3 мс на шаг 80 мс (≤ ~3% ядра) с загрузкой моделей. Реальный RVC-прогон (`rvc-python` на MiniPC, качество/задержка на предложение) требует стенда.

### 7.10. Сборка и автообновление

- Tauri 2 bundler, NSIS `setup.exe`, `installMode: currentUser`; MSI не нужен.
- Автообновление через `@tauri-apps/plugin-updater`; подпись через `tauri signer generate`.
- Приватный ключ и пароль только в GitHub Secrets: `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Тестовый ключ `client/src-tauri/updater-test/test.key` закоммичен осознанно и отличен от `pubkey` в `tauri.conf.json`; подставлять его в конфиг нельзя.

### 7.11. Надёжность Windows/Linux

Для Tauri на Linux используется [WebKitGTK](https://v2.tauri.app/develop/debug/linux-graphics/), на Windows — [WebView2](https://v2.tauri.app/start/prerequisites/#webview2). При смене стека пересмотреть платформенные меры, не переносить WebKit-переменные в Electron или другой runtime.

- [ ] **Графика до инициализации WebView:** Linux-only выбор `auto / wayland / x11 / compatibility`, сохранение ручного режима восстановления вне пакета. Не отключать ускорение всем. На машине владельца (CachyOS/Arch + KDE Wayland + NVIDIA) native Wayland с `__NV_DISABLE_EXPLICIT_SYNC=1` дал хороший результат в Owyx; это проверенный вариант одной конфигурации, не универсальный default. Отключение DMABUF устраняло серое окно, но замедляло интерфейс: оставить его совместимым режимом восстановления. Настройки применять до GTK/WebView; учитывать явные пользовательские overrides.
- [ ] **Библиотеки готового пакета:** сравнивать bundled и system WebKit/GTK на одном release executable. В Owyx на указанной машине измерено примерно 30 против 60 FPS; для Нейры это гипотеза до собственного замера. Предусмотреть необязательный system runtime с проверкой зависимостей, понятной диагностикой и fallback к bundled.
- [ ] **Окружение дочерних процессов:** CLI, браузер, терминал и вспомогательные команды ОС не наследуют AppImage-пути библиотек и GTK/GIO/GDK/WebKit. Отсутствующий, пустой и пользовательский `LD_LIBRARY_PATH` различаются; sync (`std::process`) и async (`tokio::process`) покрыты тестами. `APPIMAGE` остаётся у родительского процесса — его читает updater. Отдельного sidecar нет; новый запуск обязан идти через `appimage_env`. AR-6: поиск `PATH` на Windows без учёта регистра имён переменных, тесты `PATH`/`Path`/`path`/`pAtH`. Приёмка текущего AppImage на машине владельца остаётся открытой.
- [ ] **Наблюдатели файлов:** если клиент наблюдает проекты, логи или кэш, отфильтровать события чтения до debounce; сохранить изменение, создание, rename, удаление и завершение записи. Проверить отсутствие цикла «прочитали → watcher → пересканировали». Сейчас событийного watcher нет: каталог команд опрашивается по имени, размеру и mtime.
- [ ] **Производительность по замерам:** фиксировать CPU/диск в простое, задержку ввода и прокрутки, время стадий запуска; записывать ОС, драйвер, graphics/backend и режим библиотек. Сканирование/хеширование/запись — вне UI thread. Каркас: opt-in `NEYRA_PERF=1`, локальный JSONL стадий запуска с ротацией, `devtools/perf-report`; описание — `client/docs/PERFORMANCE.md`. Streaming объединяется таймером 60 мс без idle polling.
- [ ] **Изоляция Windows:** Linux env/workarounds ограничены платформой. На Windows отдельно проверить установку/WebView2, CLI и браузер, пути с пробелами/кириллицей, завершение дочерних процессов, закрытие и повторный запуск.
- [ ] **Настоящее обновление N → N+1:** подписанные updater-артефакты, согласованная версия и сохранение адреса/токена/темы/runtime-настроек. Для AppImage сохранить путь исходного файла, проверить обновление в system-runtime режиме и повторный запуск. Re-exec с подставленным окружением не считать проверкой обновления.
- [ ] **Release-приёмка на обеих системах:** готовый Windows installer и готовый Linux-пакет на машине владельца; запуск, простой, длинный чат, streaming, прокрутка, файловые операции, CLI, закрытие/повторный запуск, обновление с предыдущей версии.

Выбор WebView graphics backend и разрешения `host bridge` — независимые проверки: native Wayland UI сам по себе не даёт управление окнами/вводом; Win32/X11/portal capabilities проверяются отдельно.

Сверять реализацию с соседним репозиторием Owyx: `docs/LINUX.md`, `apps/app/src/linux_graphics.rs`, `apps/app/src/linux_runtime.rs`, `packages/app-lib/src/util/appimage_env.rs`; фильтрация watcher — `packages/app-lib/src/state/instances/watcher/change_watcher.rs`. Переносить проверенные решения с адаптацией к границам Нейры, не код целиком и не глобальные обходные настройки.

### 9.1. Канон публикации

```text
Клиент / браузер
  → https://neyra.owyx.site  (+ wss://…/api/v1/ws/chat)
  → nginx/Caddy на VPS (TLS)
  → frps (HTTP vhost)
  → frpc на домашнем сервере
  → Control API 127.0.0.1:8787
```

Серверные данные (память, `.env`, серверные логи, модели) остаются на **домашнем** сервере; на VPS только proxy + frps. Docker Compose на VPS — запасной стенд, не замена канону. Bind по умолчанию loopback; наружу только через frp. Токены обязательны при внешнем доступе. IP/rate-limit/setup-guard — в security-model / reverse-proxy docs (не дублировать здесь).

Пример `frpc` (секреты не в git): `type=http`, `localPort=8787`, `customDomains=["neyra.owyx.site"]`; `api.public_base_url` + `api.public_path_prefix: /api`.

`host bridge` (§7.6) использует исходящее подключение клиента через этот защищённый маршрут, без открытого порта управления на ПК. До реализации определить отдельные роли/доступ к устройству, схемы `client_tool_call/result`, capabilities, отмену и version negotiation; проверить WSS через reverse proxy, disconnect/reconnect и несколько клиентов.

Код не начинать до отдельного design/issue после защиты. Не заменять `core/` готовым агентом (Hermes / Herald-OS и т.п.) — только свой модуль.

**Архитектура:**

- Модуль `server/modules/desktop` (или `workspace`): руки и стол; ядро остаётся мозгом (память, LLM, Event Bus, Control API).
- Действия — через Event Bus и plugin invoke / Control API, без оркестрации в клиенте.
- **Гибрид (выбранный путь):** Phase A — sandbox (своя FS под `server/data/desktop/`, shell в jail/Docker, таймауты и лимиты ресурсов); Phase B — host surface (окна / computer-use / запуск приложений и игр на GPU MiniPC только по allowlist, опасные действия — с confirm).

**Слои (идеи):** `files` — дерево workspace; `shell` — команды в песочнице; `session` — что «открыто», состояние сессии; позже `display` (обзор стола), `apps`/games на хосте.

**Не сейчас:** полный GUI десктопа в дашборде/клиенте до завершения серверной части и §7; игры и computer-use до стабилизации sandbox; перенос оркестрации на внешний agent runtime.

### 11.3. Agent loop: качество ответов и фоновая память

Идея: вместо одного большого вызова модели Нейра для сложных задач работает в цикле: сама строит следующий шаг, проверяет результат и решает, готово ли. Цикл улучшает качество, а не скорость (каждая итерация — ещё один вызов модели), поэтому через него идёт не всё.

- **Роутер на входе.** Простые реплики отвечаются сразу одним вызовом, сложные (многошаговые, с поиском, с инструментами) уходят в цикл. Задержка на коротких сообщениях не растёт.
- **Цикл для сложного.** План, затем шаги, затем самопроверка и ответ. Лимиты: максимум итераций, бюджет токенов, явное условие остановки. Шаги публикуются в Event Bus и видны в дашборде.
- **Подтягивание контекста.** Перед ответом цикл сам решает, что достать из Memory Hub (точечный retrieval), а не грузит всё подряд.
- **Фоновая память.** После диалога отдельный проход без спешки решает, что запомнить, сжимает и сливает дубли, помечает устаревшее. Пользователь его не ждёт.

**Не сейчас:** реализация до стабилизации §2.2 и §8.5; сложные мультиагентные схемы.

- [x] Раздел записан в PLAN.
- [ ] Отдельный design/issue: критерии роутера, лимиты цикла, формат событий.
- [ ] MVP: роутер + фоновый проход памяти, цикл для сложного вторым шагом.

### 11.4. Голос в Discord (схема из двух ботов)

**Отложено после ВКР либо при наличии времени (уточнение 2026-10-16).** Второй бот и голосовой спайк не входят в ближайшую серверную очередь.

- **Бот 1, Нейра:** заходит в войс, слушает через `discord-ext-voice-recv` и отвечает голосом. Для приёма DAVE E2EE нужен voice-recv из ветки с `DaveSession` из discord.py, не из pip.
- **Бот 2, музыка:** текущий Lavalink (`server/modules/discord/music.py`). Отдельный бот нужен, потому что discord.py допускает один voice client на гильдию для каждого бота.
- **Пайплайн:** Silero VAD + определение конца фразы по образцу `MCKRUZ/openclaw-voice`; STT/TTS на сервере через OpenAI-совместимые `/v1/audio/transcriptions` и `/v1/audio/speech`; LLM через текущий бэкенд.
- **Сверка:** `abishop1990/discord-ai-voice` как пример приёма звука с DAVE.
- **Риски:** поддержка DAVE на приёме официально не смёрджена; у openclaw-voice нет лицензии, поэтому берём идеи, не код.

- [ ] Спайк: Нейра заходит в войс с DAVE и сохраняет полученный звук в WAV. Если приём не работает, остальные части не начинаем.
- [ ] После успешного спайка: VAD/конец фразы → STT → текущий LLM → TTS → ответ в войс; музыка остаётся на втором боте.
