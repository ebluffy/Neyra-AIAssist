# Отложенные баги

## BUG-2026-10-14-01 — создание плагина обращается к OpenRouter и завершается 404

Статус: дефект выбора провайдера исправлен локально в PR #27.
Причина: отдельные OpenRouter defaults и ключ обходили настройки brain. Теперь
PluginBuilder использует `llm.coder_model` либо настроенный brain через общий
resolver (provider/endpoint/key/headers). YAML и секреты не передаются модели.
Offline-регрессии проверяют явный coder, fallback brain на другом провайдере и
защиту существующего config.yaml. Реальные успешные вызовы/причина прежнего
404 остаются отдельной live-приёмкой пользователя.
Источник: пользовательский лог стенда, 14 октября 2026, 22:26 (Москва).

**Сценарий:** попросить Нейру создать для себя модуль. В наблюдаемом случае инструмент `create_or_edit_plugin` получил `plugin_id=server_stress_test`.

**Наблюдение:** обычные вызовы brain/talk в этом логе идут через AIHope, а PluginBuilder отдельно вызывает OpenRouter с моделью `tencent/hy3-preview:free`. Запрос завершается HTTP 404; создание плагина не завершается успешно.

```text
22:26:44,666 neyra.plugin_builder: PluginBuilder: start | plugin_id=server_stress_test existed=False
22:26:44,666 neyra.plugin_builder: PluginBuilder: call OpenRouter coder | model=tencent/hy3-preview:free
22:26:45,161 neyra.tools: Tool create_or_edit_plugin: failed | plugin_id=server_stress_test
httpx.HTTPStatusError: Client error '404 Not Found' for url 'https://openrouter.ai/api/v1/chat/completions'
```

В стеке стенда: `core/tools/builtins.py:656` → `core/plugins/builder.py:214` (`_call_openrouter_chat`) → `core/plugins/builder.py:134` (`raise_for_status`). Номера строк относятся к версии на стенде.

**Ожидаемое поведение:** создание модуля использует явно настроенного провайдера и модель для генерации кода. По ожиданию пользователя, текущая настройка должна вести к используемому провайдеру, а не неожиданно переключаться на OpenRouter.

**Гипотеза пользователя:** в PluginBuilder осталась жёсткая привязка к OpenRouter или его модели. Причина 404 пока не установлена: сам лог не доказывает, что ошибка вызвана именно endpoint, а не недоступностью модели или маршрута.

Перед исправлением:

- [x] Проверить выбор провайдера, endpoint и модели в PluginBuilder и слои конфигурации.
- [x] Ошибки инструмента возвращают фиксированный текст без provider response/dialogue; trace хранит исход вызова без содержимого.
- [x] AR-27: этот контракт применяется и к штатным `ok: false`, не только к исключениям. Tool-регрессии покрывают JSON parse/write/manifest/exception; поля raw и error не сериализуются в ответ модели.
- [x] AR-28: штатная причина отказа доступна оператору в server warning (до 2000 символов); raw не логируется. caplog проверяет наличие причины и отсутствие сырого ответа.
- [x] Добавить offline-регрессию маршрутизации создания плагина через настроенный провайдер.
- [ ] Live: успешное создание тестового плагина и диагностика прежнего 404 на разрешённом стенде.

## BUG-2026-10-14-03 — WebSearch использует отсутствующий backend и неверно подписывает fallback

Статус: подтверждена проблема диагностики/выбора backend; локально исправлена обработка ошибок.
Наблюдение -> причина: runtime DDGS отвергал неподдерживаемый backend и fallback маркировался именем запроса; список backend зависит от версии библиотеки.
Изменение -> тест: ошибки поиска больше не выводят traceback/query; compileall выполнен. Полный provider matrix не запускался.
Остаточная live-приёмка: проверить фактически используемый backend на установленной версии DDGS.
Источник: полный пользовательский фрагмент лога, 14 октября 2026, 22:22 (Москва).

```text
22:22:39,476 ddgs.ddgs: yandex - backends do not exist or are disabled. Available: brave, duckduckgo, google, grokipedia, mojeek, startpage, wikipedia, yahoo
22:22:39,476 ddgs.ddgs: backend is not set. Using 'auto'
22:22:46,118 neyra.tools: WebSearch backend success | engine=yandex query=<removed>
```

Библиотека явно отклоняет `yandex` и включает `auto`, но приложение затем сообщает об успехе `engine=yandex`. Фактический источник результата по этому логу установить нельзя. До этого видны пустые результаты нескольких движков, HTTP 403 и timeout; пустая выдача сама по себе не доказывает баг поиска.

- [ ] Проверить список поддерживаемых движков относительно установленной версии DDGS и настройки поиска.
- [ ] Различать запрошенный backend и реально использованный fallback; не приписывать результат отсутствующему движку.

## BUG-2026-10-14-05 — AIHope возвращает 502, обновление working_memory срывается

Статус: внешний 502 подтверждён; blocking ответа не доказан, background guard уже присутствует.
Наблюдение -> причина: provider 502 срывает конкретное WM обновление; приложение логирует компактно и не поднимает ошибку в чат.
Изменение -> тест: существующая async isolation сохранена; compileall выполнен.
Остаточная live-приёмка: проверить повторное обновление и сохранность предыдущего snapshot после provider recovery.
Источник: тот же лог, 14 октября 2026, 22:39–22:40 (Москва).

```text
22:39:28,093 httpx2: HTTP Request: POST https://aihope.fun/v1/chat/completions "HTTP/1.1 502 Bad Gateway"
22:39:28,094 openai._base_client: Retrying request in 60.000000 seconds (retry 1 of 1)
22:40:46,926 httpx2: HTTP Request: POST https://aihope.fun/v1/chat/completions "HTTP/1.1 502 Bad Gateway"
```

Ответ Cloudflare сообщает `origin_bad_gateway`, `retryable=true`, `retry_after=60`: сбой origin провайдера. SDK запланировал минутное ожидание; по фрагменту без корреляции нельзя связать оба 502 с одним запросом или доказать блокировку чата. В 22:40:50 есть успешное обновление памяти другого пользователя — это не подтверждает восстановление неудачного обновления.

- [ ] Проверить, сохраняется ли предыдущая working_memory при ошибке и будет ли повторное обновление.
- [ ] Проверить, что длительный retry фоновой памяти не задерживает ответ пользователя.
- [ ] Добавить безопасную корреляцию вызовов и компактную диагностику ошибки вместо полного тела ответа провайдера.

Наблюдение -> причина: query/URL/exception попадали в INFO/error logs, включая library loggers.
Изменение -> тест: библиотечные loggers подключены к redaction filter, web_search больше не пишет traceback/details; compileall выполнен.

- [ ] Убрать или редактировать содержимое поисковых запросов в обычных логах приложения и библиотек.
- [ ] Проверить причину запуска WebSearch для личной разговорной реплики. Без исходного хода и результатов инструмента нельзя утверждать, что выбор инструмента ошибочен.

## BUG-2026-10-14-07 — GIF в Discord ошибочно запускает музыкальное воспроизведение

Статус: риск подтверждён по маршрутизации и исправлен локально; live-воспроизведение не выполнялось.
Наблюдение -> причина: GIF/media text мог пройти soft music candidate без явного play verb.
Изменение -> тест: GIF без play не создаёт music candidate; явный play сохраняется; compileall выполнен.
Остаточная live-приёмка: проверить Tenor/Discord CDN attachment/embed и voice validation до подключения.
Источник: Discord, 14 октября 2026, 23:15 (время на скриншоте).

**Сценарий:** участник отправляет GIF в текстовый канал без просьбы воспроизвести музыку. По наблюдению пользователя, Нейра подключается к voice для воспроизведения. На скриншоте бот отвечает на сообщение с GIF ошибкой «Не получилось», «Команда не выполнена», «Поддерживаются только ссылки на видео YouTube».

**Ожидаемое поведение:** обычная отправка GIF сама по себе не запускает музыкальную команду и не подключает бота к voice. Неподдерживаемая ссылка при явном запросе воспроизведения должна отклоняться до подключения к voice.

**Неизвестное:** пользователь предполагает ссылку Tenor; исходный URL и тип сообщения (ссылка/embed/attachment) на скриншоте не видны. Сам вход в voice подтверждён сообщением пользователя, а не скриншотом. Причина выбора музыкального маршрута пока не установлена.

- [ ] Проверить музыкальную маршрутизацию GIF-ссылок Tenor/Discord CDN, embed и attachment без явного запроса музыки.
- [ ] Проверить валидацию типа ссылки и намерения до подключения к voice.
- [ ] Добавить offline-регрессии: GIF не вызывает music/voice; явный запрос с неподдерживаемой ссылкой не подключает voice; обычный запрос YouTube продолжает работать.
