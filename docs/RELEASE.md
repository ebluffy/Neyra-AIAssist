# Выпуск клиента Neyra

## Known limitation (PR #44, AR3)

Настройка подписи updater и проверка настоящего обновления вынесены в отдельную
задачу владельца. Приватного ключа для текущей заготовки
`plugins.updater.pubkey` нет; конфигурация подписи оставлена без изменений.
Без настройки ключа и GitHub Secrets релизный workflow не готов к выпуску.
Зелёный CI не подтверждает публикацию релиза или обновление AppImage.

Отложенные проверки владельца (не выполнены в рамках PR #44):

- Настроить ключ подписи и секреты `TAURI_SIGNING_PRIVATE_KEY` и
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` по инструкции ниже.
- Прогнать тег `client-v…`, проверить опубликованные артефакты, подписи и
  `latest.json`, включая `client-beta/latest.json`.
- Проверить N → N+1 через кнопку «Обновления» в AppImage на стабильном и
  бета-канале по [инструкции приёмки](../client/docs/ACCEPTANCE-LINUX.md#шаг-8-n--n1).

Перечисленные пункты остаются открытыми критериями приёмки в интеграционном
PR #36. По команде владельца от 2026-11-04 PR #44 поставляет код workflow
в ветку #36; настройка production-подписи, публикация и живое обновление
не заявляются выполненными.

## Порядок выпуска

1. Один раз на компьютере владельца создайте ключ обновлений (не добавляйте ключ в Git):

   ```sh
   cd client
   npx tauri signer generate -w ~/.tauri/neyra.key
   ```

   Сохраните резервную копию закрытого ключа и пароль. Потеря ключа означает,
   что установленные клиенты нельзя будет обновить без переустановки.

2. Поместите **публичный** ключ из `~/.tauri/neyra.key.pub` в
   `client/src-tauri/tauri.conf.json` (`plugins.updater.pubkey`) и закоммитьте
   конфигурацию. Не используйте тестовый ключ из репозитория.

3. В настройках репозитория GitHub (`Settings` -> `Secrets and variables` ->
   `Actions`) добавьте секреты `TAURI_SIGNING_PRIVATE_KEY` (содержимое
   `~/.tauri/neyra.key`) и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (пароль от ключа).

4. Обновите одну и ту же версию в `client/package.json`,
   `client/src-tauri/tauri.conf.json`, `client/src-tauri/Cargo.toml` и
   `client/src-tauri/Cargo.lock`. Проверьте командой
   `node client/scripts/check-versions.mjs client-v<версия>` из корня репозитория.
   Закоммитьте изменения, создайте и отправьте тег:

   ```sh
   git tag client-v<версия>
   git push origin client-v<версия>
   ```

5. Проверьте успешное завершение всех заданий `Desktop release` в GitHub
   Actions и опубликованный релиз с установщиками, подписями и `latest.json`.
   Можно также вручную запустить workflow с уже созданным тегом через
   `workflow_dispatch`.

Тег с суффиксом, например `client-v0.2.0-beta.1`, публикуется как prerelease.
GitHub `releases/latest` не возвращает prerelease. После публикации workflow
создаёт или обновляет rolling prerelease `client-beta` с `latest.json` только
если новая версия новее текущей в смысле SemVer. Стабильные релизы тоже
обновляют этот канал, если они новее; ссылки на установщики в манифесте ведут
к исходному релизу. Проверьте оба канала после первого выпуска.
Ошибка чтения фида или невалидная версия в манифесте останавливают обновление
бета-фида.
