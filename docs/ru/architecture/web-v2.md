# Web v2 — собственный клиент Нейры

> **Статус:** draft-спека, 11.11.2026. Заменяет план интеграции с Open WebUI (issue #66).
> **Область:** §3a.2 `docs/PLAN.md`. Разделы §0 (паспорт ВКР) и §9 (рабочий стол Нейры) не меняются.
> **Нормативная версия:** русская. Английская — после ревью спеки.

## 1. Контекст

Сейчас веб — это `server/dashboard/`: ops-консоль с одним ключом доступа (PBKDF2, сессия в `sessionStorage`), экранами «Статус», «Модули», «Память», «Система», «Вебхуки», «Настройки», «API Docs». В ней нет чата, аккаунтов, ролей и пользовательских данных. Это админский пульт, а не продукт.

Issue #66 предлагал использовать Open WebUI как прослойку: аккаунты и чаты в OWUI, ядро Нейры за OpenAI-совместимым API. Решение от 11.11.2026 это отменяет: OWUI не форкаем и не разворачиваем как продуктовый фронт. Причина — необходимость своего UX, брендинга и полного доступа к ядру, а также нежелание тащить чужой форк и его лицензионные ограничения.

Требования из #66 (аккаунты, чат, память по пользователю, синхронизация истории с десктопом, доверенная идентичность) сохраняются и переносятся в собственную реализацию.

## 2. Решения

| # | Решение | Обоснование |
|---|---------|-------------|
| D1 | Свой веб-клиент вместо OWUI и вместо форка | Контроль UX, брендинг, отсутствие форк-долга |
| D2 | Веб — отдельный сервис от ядра | Ядро остаётся systemd-процессом с плагинами; веб деплоится и обновляется независимо |
| D3 | Next.js (App Router) + Better Auth + PostgreSQL + Drizzle | Один процесс на UI, API и авторизацию; готовые OAuth, сессии, роли |
| D4 | UI: Tailwind + shadcn/ui + assistant-ui; структура как у Open WebUI | Быстрый качественный чат-UX без копирования чужого кода |
| D5 | Роли: `admin`, `user`, `guest` | Guest — только лендинг и демо, без чата |
| D6 | Регистрация настраивается админом: одобрение, инвайты, открытая, закрытая | Полный контроль над тем, кто попадает на сервер |
| D7 | Вход: email+пароль, логин+пароль без email, Discord OAuth | Email не обязателен; SMTP в v1 нет, письма закладываются на будущее |
| D8 | Модели: «Нейра» по умолчанию + добавление Ollama и любых OpenAI-совместимых | Нейра — основной ассистент; остальное для личного пользования админа |
| D9 | Память в UI: факты, дневник, LTM — просмотр, правка, удаление | Память остаётся в ядре, веб — интерфейс к ней |
| D10 | Вложения: текст, изображения, файлы, голос (STT/TTS) | Полный чат, а не только текст |
| D11 | История: поиск, pin, папки, шаринг, экспорт, ветвление сообщений | Паритет с OWUI по основным сценариям |
| D12 | Тёмная тема по умолчанию, светлая — переключателем; нейтральная палитра | Как в OWUI: без фиолетовых градиентов и «неона» |
| D13 | RU сейчас, i18n заложить с первого коммита | Английский — после v2 |
| D14 | Старый дэшборд выводится из эксплуатации после паритета; `/legacy` на время миграции | Не терять доступ к ops-функциям в переходный период |

## 3. Цели и не-цели

**Цели v1:**

- Веб-чат с Нейрой: стриминг, история, вложения, голос.
- Аккаунты, роли, группы доступа, одобрение регистрации.
- Память пользователя: факты, дневник, LTM.
- Полная админка ядра: статус, модули, вебхуки, настройки, провайдеры моделей, бэкапы, логи, рестарт.
- Один сайт: пользовательская часть и админка в одном приложении.

**Не-цели v1:**

- Публичная соцсеть, лента, комментарии.
- Собственный RAG-движок: знания остаются у Нейры.
- Мобильные приложения: только план (см. §18).
- Федерация, мультитенантность, биллинг.
- Замена Discord/Telegram: они остаются отдельными каналами.

## 4. Роли

| Возможность | guest | user | admin |
|---|---|---|---|
| Лендинг и демо | ✓ | ✓ | ✓ |
| Чат с Нейрой | — | ✓ | ✓ |
| Своя история и память | — | ✓ | ✓ |
| Выбор разрешённых моделей | — | ✓ | ✓ |
| Свои API-ключи для внешних клиентов | — | — | ✓ |
| Чтение чужих чатов | — | — | ✓ |
| Пользователи, роли, баны | — | — | ✓ |
| Модели, ключи, лимиты | — | — | ✓ |
| Ops: модули, вебхуки, бэкапы, рестарт | — | — | ✓ |
| Аудит | — | — | ✓ |

`guest` не создаёт чатов и не получает person-запись в памяти. Демо-страница работает без сохранения.

## 5. Регистрация и вход

### 5.1. Режимы (переключатель в админке)

| Режим | Поведение |
|---|---|
| `approval` (по умолчанию) | Форма → статус `pending` → админ одобряет или отклоняет |
| `invite` | Без кода регистрация невозможна; код создаёт админ, у кода лимит использований и срок |
| `open` | Сразу активный аккаунт; включать только осознанно |
| `closed` | Саморегистрации нет; пользователей создаёт админ |

Режим — глобальная настройка. OAuth-входы подчиняются тому же правилу: новый Discord-аккаунт попадает в `pending`, если включён `approval`.

### 5.2. Способы входа (включаются отдельно)

- Email + пароль.
- Логин + пароль без email.
- Discord OAuth.
- Позже: Telegram, Google, GitHub.

Один пользователь может иметь несколько способов входа; привязка — через таблицу `accounts`. Слияние аккаунтов по email по умолчанию выключено: email может быть не подтверждён.

### 5.3. Email и пароли

- В v1 SMTP нет: письма не отправляются, email не подтверждается.
- Восстановление пароля — админом из админки.
- Если email не задан, используется логин; оба уникальны.
- Пароль: минимум 10 символов, хеш — средствами Better Auth (scrypt/argon2), сырой пароль не логируется.
- Сессия: HttpOnly cookie, SameSite=Lax, срок 30 дней, отзыв всех сессий из админки.
- Rate limit на вход и регистрацию по IP и по аккаунту.

### 5.4. Discord

- OAuth2 scope: `identify email` (email опционален, Discord может его не отдать).
- `discordId` сохраняется и используется для привязки к Discord-боту Нейры.
- При первом входе создаётся аккаунт в статусе согласно режиму регистрации.

## 6. Архитектура

```mermaid
flowchart LR
  B["Браузер"] -->|HTTPS| NX["nginx / Cloudflare / frpc"]
  NX -->|"/" и "/api/*"| W["web: Next.js"]
  NX -->|"/v1/desktop/*"| C["Ядро Нейры: FastAPI"]
  NX -.->|"/legacy/*"| L["Старый dashboard"]
  W -->|"PostgreSQL"| DB[("web DB")]
  W -->|"внутренний HTTP + JWT"| C
  C --> OL["Ollama"]
  C --> P["OpenAI-совместимые провайдеры"]
  D["Desktop Tauri"] -->|"чат и история"| W
  D -->|"bridge и voice"| C
```

**Компоненты:**

- `web/` — новый каталог в репозитории (Next.js). Владеет аккаунтами, чатами, настройками UI и админкой. Своя БД.
- `server/` — ядро Нейры. Владеет памятью, моделями, инструментами, модулями, голосом. Своя SQLite.
- Обмен — только по внутренней сети: `http://127.0.0.1:8787`.

**Почему Next.js, а не Vite SPA:** нужен серверный слой для auth, OAuth-callback, cookies и проксирования к ядру. Отдельный FastAPI-BFF дал бы два бэкенда и свою реализацию авторизации. Next.js в standalone-режиме — один процесс, ~250–400 МБ RSS, что для MiniPC приемлемо.

**Почему отдельный сервис:** ядро запускается systemd-юнитом и не должно перезапускаться при обновлении фронта. Веб обновляется контейнером или отдельным юнитом.

## 7. Данные

PostgreSQL, схема `public`, миграции — Drizzle.

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | Аккаунты | `id`, `email?`, `username`, `display_name`, `role`, `status`, `password_hash?`, `email_verified`, `created_at`, `approved_by`, `banned_at`, `ban_reason` |
| `accounts` | OAuth-привязки | `provider`, `provider_account_id`, `user_id`, `discord_id` |
| `sessions` | Сессии | `id`, `user_id`, `expires_at`, `ip`, `user_agent` |
| `invites` | Инвайты | `code`, `created_by`, `max_uses`, `used`, `expires_at` |
| `folders` | Папки чатов | `id`, `user_id`, `name`, `position` |
| `conversations` | Чаты | `id`, `user_id`, `title`, `model`, `pinned`, `folder_id`, `created_at`, `updated_at`, `archived_at` |
| `messages` | Сообщения | `id`, `conversation_id`, `parent_id?`, `role`, `content` (jsonb), `model`, `tokens_in`, `tokens_out`, `status`, `error_code`, `created_at` |
| `attachments` | Вложения | `id`, `message_id`, `kind`, `path`, `mime`, `size`, `meta` (jsonb) |
| `shares` | Публичные ссылки | `id`, `conversation_id`, `token`, `expires_at`, `created_by` |
| `model_providers` | Провайдеры | `id`, `kind`, `base_url`, `api_key_enc`, `enabled` |
| `models` | Модели | `id`, `provider_id`, `model_id`, `label`, `visibility`, `allowed_roles`, `is_default` |
| `user_settings` | Настройки пользователя | `user_id`, `theme`, `density`, `default_model`, `language` |
| `memory_map` | Связь с ядром | `user_id`, `person_id` (`web:<uuid>`), `created_at` |
| `audit_log` | Аудит | `id`, `actor_id`, `action`, `target`, `meta`, `created_at` |

Правила:

- Дерево сообщений — через `parent_id`; активная ветка хранится в `conversations.active_leaf_id`.
- Удаление чата — soft delete (`archived_at`), физическое удаление — по политике хранения.
- Удаление пользователя: аккаунт и чаты удаляются; память в ядре помечается на очистку и удаляется отдельной операцией.
- Вложения — на диске (`/opt/neyra/web/data/uploads`), в БД только метаданные.

## 8. Идентичность и доверие

Веб — единственный источник идентичности для веб-чата.

1. Web подписывает короткоживущий JWT (HS256, TTL 60 с) секретом `NEYRA_IDENTITY_JWT_SECRET`.
2. Запрос к ядру: `Authorization: Bearer <service-key>` + `X-Neyra-Identity: <jwt>`.
3. Claims: `sub` (web user id), `role`, `name`, `chat_id`, `message_id`, `task`, `iat`, `exp`.
4. Ядро проверяет подпись, срок и `iss`, затем маппит `sub` → `person_id` (`web:<sub>`).
5. Ошибка проверки — 401, без доверия к заголовкам. Fail-closed.

Заголовки `X-Neyra-*` без валидного JWT игнорируются. Прямой доступ из интернета к `/v1/openai/*` и `/v1/web/*` запрещён на nginx; эти префиксы доступны только из docker-сети/loopback.

## 9. Чат

**Базовый сценарий:** пользователь открывает чат → выбирает модель (по умолчанию «Нейра») → отправляет сообщение → SSE-стрим → сообщение и ответ сохраняются в `messages`.

Функции v1:

- Стриминг с кнопкой «Стоп».
- Регенерация ответа, редактирование сообщения, ветвление (дерево).
- Markdown, код с подсветкой и копированием, таблицы, mermaid.
- Вложения: изображения (vision), текстовые файлы и PDF (извлечение текста), аудио (STT).
- Голос: запись с микрофона → STT; озвучка ответа → TTS. Аудио проксируется через web в ядро.
- Заголовок чата генерируется дешёвой моделью; ошибка генерации не ломает чат.
- Поиск по чатам, pin, папки, архив.
- Шаринг ссылкой (read-only, срок жизни, отзыв).
- Экспорт чата в Markdown/JSON.
- Индикатор «память обновилась» без раскрытия приватных фактов.

**Контракт с ядром:** OpenAI-совместимый `POST /v1/openai/chat/completions` (`stream: true`) плюс заголовки идентичности. История передаётся ядру как есть; ключ сессии — `chat_id`.

## 10. Память

Память живёт в ядре; веб — интерфейс.

Разделы:

- **Факты** — список по человеку, поиск, правка, удаление, источник (канал, дата).
- **Дневник** — записи Нейры по дням, фильтр по датам, удаление.
- **LTM** — долговременные записи, просмотр и очистка.

Правила:

- Пользователь видит только свою память (`person_id` = `web:<user_id>`).
- Админ видит всё, действие попадает в аудит.
- Правка из UI идёт через API ядра, а не напрямую в SQLite.
- Удаление факта не удаляет исходные сообщения; связь показывается явно.

## 11. Модели

- «Нейра» — модель по умолчанию, публичная, доступна всем пользователям.
- Админ добавляет провайдеров: Ollama (локально) и любые OpenAI-совместимые (base URL + ключ).
- Для каждой модели: `visibility` (`public` / `private`), `allowed_roles`, лимиты.
- `private`-модели видит только админ; «скрыть» вместо `private` не используется — скрытая модель остаётся доступной по API.
- Ключи провайдеров шифруются в БД (AES-GCM, мастер-ключ в env), в UI показываются маской.
- Проверка соединения и список моделей — кнопкой в админке.

## 13. UI/UX

**Структура (как у Open WebUI, но свой код и брендинг):**

- Слева — сайдбар: новый чат, поиск, папки, список чатов, низ — профиль и настройки.
- Центр — чат: заголовок, выбор модели, лента, композер с вложениями и микрофоном.
- Справа — выдвижная панель: параметры модели, память, вложения.
- Настройки — модальное окно с разделами.
- Админка — отдельная секция в том же сайдбаре.

**Визуал:**

- Нейтральная палитра (графит/серый), один акцент — фирменный cyan Нейры.
- Тёмная тема по умолчанию, светлая — переключателем; без фиолетовых градиентов, орбов, glassmorphism и неона.
- Радиусы 8–12 px, тонкие границы, плотные списки.
- Шрифт UI — нейтральный sans (системный стек или Inter-подобный), код — Fira Code. Старый `DESIGN.md` не наследуется, для v2 пишется новый.
- Иконки — Lucide, одинаковый stroke.
- Анимации ≤200 мс, уважать `prefers-reduced-motion`.

**Доступность:** контраст ≥ 4.5:1, видимый focus-ring, полная клавиатурная навигация, ⌘K, корректные aria-атрибуты, цели ≥ 40 px.

**Адаптив:** desktop-first; на планшете сайдбар сворачивается, на телефоне — drawer. Мобильное приложение — отдельный этап.

**i18n:** все строки через словари с первого коммита (`ru` по умолчанию, `en` заготовка).

## 14. Деплой

```
/opt/neyra/            # ядро, systemd neyra.service, SQLite
/opt/neyra/web/        # веб v2: compose или systemd
  docker-compose.yml   # app + postgres
  data/uploads/
  .env
```

- Ядро слушает `127.0.0.1:8787` (и внутренний адрес для web в docker-сети).
- Web слушает `127.0.0.1:3000`, публикуется через nginx.
- nginx на хосте: `/` → web, `/v1/desktop/*` → ядро, `/legacy/*` → старый dashboard, `/v1/openai/*` и `/v1/web/*` → deny снаружи.
- Домен `neyra.owyx.site` сохраняется, TLS — как сейчас (Cloudflare + frpc).
- Ресурсы: web ~250–400 МБ, Postgres ~150 МБ. Контроль через `docker stats`/systemd.
- Бэкап: `pg_dump` ежедневно + существующий бэкап ядра; проверка восстановления раз в месяц.
- Обновление: pinned-теги образов, миграции при старте, откат на предыдущий тег.

Переменные окружения web:

```
DATABASE_URL=
BETTER_AUTH_SECRET=
BETTER_AUTH_URL=https://neyra.owyx.site
NEYRA_BASE_URL=http://127.0.0.1:8787
NEYRA_SERVICE_KEY=
NEYRA_IDENTITY_JWT_SECRET=
DISCORD_CLIENT_ID=
DISCORD_CLIENT_SECRET=
UPLOAD_DIR=/data/uploads
```

Секреты — только в env/секретах, не в репозитории и не в БД в открытом виде.

## 15. Изменения в ядре

Минимальные, без переписывания:

1. Проверка `X-Neyra-Identity` на `/v1/openai/*`, `/v1/web/*`, `/v1/desktop/*`.
2. Namespace `/v1/web/memory/*`: список/правка/удаление фактов, дневника, LTM с проверкой роли.
3. HTTP-обёртка для STT/TTS веба (переиспользовать `/v1/desktop/voice` или добавить `/v1/web/voice`).
4. Маппинг `web:<user_id>` → `person_id` при первом ходе.
5. Отключение старого dashboard-гейта после миграции (код не удалять до отдельного решения).

## 16. Безопасность и приватность

- Пароли — только хеши; секреты не попадают в логи.
- CSRF-защита для мутаций, проверка Origin.
- Rate limits: вход, регистрация, чат, загрузка файлов.
- Загрузки: проверка MIME и размера, хранение вне webroot, отдача через авторизованный endpoint.
- Шаринг-ссылки: случайный токен ≥ 32 байт, срок, отзыв.
- Админ может читать чаты — это явно написано при регистрации и в настройках.
- Аудит append-only: кто, что, когда.
- Удаление аккаунта: данные web удаляются, память ядра — по отдельной процедуре с подтверждением.

## 17. Миграция и откат

Данных чатов в старом dashboard нет, поэтому миграция — про доступ и конфигурацию.

1. Развернуть web на отдельном хосте/порте, проверить без пользователей.
2. Включить админа, проверить чат, память, модели, ops-экраны.
3. Переключить `/` на web, старый dashboard — на `/legacy`.
4. Раздать инвайты, собрать обратную связь.
5. Через 2 недели без инцидентов удалить `/legacy` и старый код.

Откат: вернуть nginx на старый dashboard, web оставить запущенным для диагностики.

## 18. Этапы

| Этап | Результат |
|---|---|
| P0 | Каркас web, БД, auth, темы, layout |

| P2 | Память: факты, дневник, LTM |

## 19. Приёмка

- [ ] Админ включает режим регистрации, пользователь регистрируется и попадает в `pending`.
- [ ] Админ одобряет; пользователь входит по паролю и по Discord.
- [ ] Чат стримит, история сохраняется после перезагрузки и видна на другом устройстве.
- [ ] Вложения: изображение, файл, голосовое сообщение.
- [ ] Память: факт появился, отредактирован и удалён из UI.
- [ ] Админ добавляет модель Ollama и OpenAI-совместимую, выдаёт доступ роли.
- [ ] Ops: статус, toggle модуля, вебхук, бэкап, рестарт.
- [ ] Тёмная и светлая темы, клавиатура, мобильная ширина.
- [ ] Снаружи недоступны `/v1/openai/*` и `/v1/web/*`.
- [ ] Старый dashboard доступен только на `/legacy` и затем удалён.

## 20. Риски

| Риск | Мера |
|---|---|
| Расползание объёма | Этапы P0–P6, каждый — отдельный PR |
| Два источника данных (Postgres + SQLite) | Чёткая граница: web — аккаунты/чаты, ядро — память/модели |
| Утечка идентичности | Подписанный JWT, service key, закрытые префиксы |
| Потеря ops-доступа при миграции | `/legacy` до паритета |
| Нагрузка на MiniPC | Лимиты, мониторинг, pinned-образы |
| Долгая разработка | Переиспользование библиотек, без собственного чат-движка |

## 21. Открытые вопросы

- SMTP и подтверждение email — когда появится провайдер писем.

- Политика хранения: сколько хранить архивные чаты и аудит.

- Целевая задержка голоса в вебе.
